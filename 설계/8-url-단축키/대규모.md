# 8. URL 단축기 설계 (대규모)

- 대상: 대규모 서비스

- 질문: 야구보구 사용자가 직관 기록이나 승률 카드를 SNS로 공유할 때 `긴 링크`가 생긴다.
경기 종료 직후의 `write burst`와 뒤이은 대규모 클릭(`read`) 속에서 어떻게 짧고 빠르게 리다이렉션할 것인가?

> **설계 원칙:** short_key에서 target_url로 가는 매핑은 한 번 정해지면 바뀌지 않는다(immutable).

> 관련 장: 6장 키-값 저장소 설계 , 7장 유일 ID 생성기 설계

---

## 1. 문제 정의 & 설계 범위 확정

- 서비스: **야구보구 공유 링크 단축기**
    - 직관 인증과 랭킹을 외부로 공유할 때 쓰는 짧은 링크를 발급하고 리다이렉션한다.
- 사용자
    - 경기 종료 직후 자신의 직관 인증을 SNS로 공유하는 사용자 (단축 생성이므로 `write`)
    - 공유받은 링크를 눌러 야구보구로 들어오는 사람 (리다이렉션이므로 `read`)
- 핵심 기능
    - 긴 딥링크를 짧은 링크로 단축 (`write`)
    - 짧은 링크를 원본 딥링크로 리다이렉션 (`read`)
    - 클릭 분석 (유입 경로, 팀, 경기, 지역) (관광 데이터 연계에 사용)
    - 야구보구 내부 링크만 단축 (외부 임의 URL은 차단)
- 제외할 범위
    - 공유 카드 이미지 생성과 렌더링
    - 딥링크가 최종적으로 여는 앱 화면 로직
    - 직관 기록 원본 저장(6장), ID 발급 자체(7장)
    - 로그인, 인증
    - 커스텀 별칭(vanity URL) 편집 UI
- 제약사항
    - **읽기가 쓰기보다 훨씬 많다** (공유 1건에 수십에서 수백 클릭)
    - 경기 종료 직후 짧은 시간에 단축 생성 작업이 몰리고(write burst), 그 후 클릭이 생성보다 더 크게 몰린다(read burst)
    - 리다이렉션이 느리면 유입이 이탈된다.
        - p99 수십 ms를 목표로 한다.
    - **한 번 발급된 짧은 링크는 불변이다.**
    - 봇과 크롤러의 대량 클릭이 트래픽에 포함된다.

### 품질 우선순위

- 1순위: `리다이렉션`(read) 가용성과 저지연.
    - 링크가 죽거나 느리면 유입 경로가 사라진다.
- 2순위: `매핑 내구성`. 생성 성공을 반환한 매핑은 유실되지 않아야 한다.
- 3순위: `단축 생성(write) 처리량`. burst를 흡수한다.
- 허용 가능한 희생
    - 클릭 분석은 **최종적 일관성** (수초에서 수분 지연 허용, 비동기 집계)
    - 클릭 수 카운트의 미세한 유실이나 중복 허용 (정확 과금이 아님)
    - 커스텀 별칭과 링크 수정 기능 포기

### 내구성 정의 (SLO)

- **생성 API가 성공을 반환한 매핑은 단일 노드 장애로 유실되지 않는다.**
- 구현: RF=3, 쓰기 LOCAL_QUORUM ACK, 주기적 스냅샷, 리전 밖 또는 object storage 백업, 정기 repair.
- 주의: replication은 backup이 아니다. 잘못된 쓰기나 삭제도 그대로 복제되므로, 영구 링크라면 백업이 별도로 필요하다.

### 규모

- DAU / MAU
    - DAU 약 500만, MAU 약 2,000만
- 클릭(read)
    - 공유 1건당 평균 20에서 50 클릭, 하루 1억에서 2.5억 클릭
    - 인기 경기 종료 직후 60%가 30분에 몰리면 평균 Peak 약 83,000 QPS, 바이럴 시 3배까지
    - 읽기 대 쓰기 약 20 대 1 이상
- 단축 생성(write)
    - 평균: 5,000,000 / 86,400 ≈ 58 writes/s
    - 경기 종료 집중: 5,000,000 x 0.6 / 1,800 ≈ 1,700 QPS
    - capacity target: 예상 peak의 5에서 10배인 `10,000에서 20,000 QPS`까지 버티게 설계해야함 (예상 트래픽X, stress target)
- 데이터 규모
    - redirect 레코드(short_key, target_url, created_at) 자체의 데이터량은 작다. 분석용 메타데이터는 분리한다.
    - 10년 100억 건 x 약 500B ≈ `5TB` raw, RF=3이면 약 `15TB`, 여기에 index와 SSTable overhead, compaction 여유, backup까지 더하면 수십 TB급
- 확인 질문
    - 가장 중요한 흐름은?
        - 경기 종료 직후 공유 링크 클릭(read) 폭증
    - 실시간 처리가 필요한가?
        - 리다이렉션은 즉시. 클릭 분석은 수초에서 수분 지연 허용.
    - 데이터 손실이나 중복을 허용하는가?
        - 생성 성공한 매핑은 유실 불가. 클릭 카운트 미세 오차는 허용.
    - 일관성은 어느 수준인가?
        - 방금 만든 링크는 곧바로 동작해야 한다(read-after-write). 분석은 최종적 일관성.
    - 기존 인프라를 활용하는가?
        - 7장 Snowflake ID 생성기, 6장 Cassandra와 MQ 집계 파이프라인, 4장 처리율 제한 장치를 재사용한다.

## 2. 개략 설계안 제시 & 동의 구하기

중규모까지는 애플리케이션에서 `해시`(예: SHA-256 앞자리)로 짧은 키를 만들고 충돌 시 재시도하며, 단일 `RDB`와 `로컬 캐시`로 리다이렉션을 감당할 수 있다. 하지만 대규모에서는 한계에 부딪힌다.

- 충돌 확인 조회 병목: 발급마다 **이미 있는 키인지를 DB에서 확인**해야 해서 `write burst` 때 병목이 된다.
- read 폭증: 경기 종료 직후 클릭이 수만에서 수십만 QPS로 몰려 **단일 저장소가 감당하지 못한다**.

<img width="1600" height="900" alt="image" src="https://github.com/user-attachments/assets/c30f94b0-daf1-48e6-bf03-82bbc0965362" />

- Write
    1. 사용자가 공유 링크 생성을 요청한다.
    2. **Snowflake**로 충돌 없는 유일 ID를 만든다.
    3. ID를 **Base62**로 인코딩해 짧은 `short_key`로 바꾼다.
    4. `short_key → long_url` 매핑을 **Cassandra에 영구 저장**한다.
        - 접근 패턴은 `short_key` 기준 단건 조회이고 JOIN이 거의 없다.
        - 여러 노드에 복제해 단일 노드 장애를 견딘다.
    5. Cassandra 저장이 성공하면 링크를 반환하고, Redis는 `best-effort`로 채운다.
        - Redis 저장에 실패해도 링크 생성은 성공으로 처리한다.
        - 첫 조회가 Cassandra까지 내려가면 그때 캐시를 다시 채운다.
- Read: 최대한 앞에서 빠르게 반환
    - **Edge HIT** → Origin까지 안 가고 Edge에서 바로 `302 Location` 응답.
    - **Edge MISS** → Origin의 `Redirect API`로 이동.
    - Redirect API는 **`Local Cache` → `Redis` → `Cassandra`** 순서로 조회.
    - Cassandra까지 갔다면 찾은 값을 Redis 등에 다시 채워서 다음 요청을 빠르게 처리.
    - 어느 단계에서 찾든 최종적으로 사용자는 **302 Redirect**를 받음.
- 기타) 클릭 분석
    - 클릭 데이터는 Edge access log나 Edge 이벤트 파이프라인에서 비동기로 수집한다. 리다이렉션과 분석을 분리하면 저지연을 제공하면서 분석도 가능하다.

### 단축 키 전략

<img width="1600" height="900" alt="image" src="https://github.com/user-attachments/assets/ad382fac-a55a-478d-a96b-1de248f3a8af" />

- 해시 + 충돌 해결 vs KGS vs 유일 ID(Snowflake) + base-62
    - **해시 + 충돌 해결**: longUrl 해시의 앞 `N자`를 쓰고 이미 있으면 `salt`를 붙여 재해시한다(+ `Bloom filter`). 짧지만(약 7자) 발급마다 충돌 확인 조회가 필요해 write burst에 불리하다.
    - **KGS**(키 생성 서비스): 짧은 키를 미리 대량으로 만들어 `큐`에 넣어두고 발급 때 꺼내 쓴다. 조회 없이 짧은 키를 제공하는 흔한 정석적인 방법이다.
    - **유일 ID + base-62**: 7장 `Snowflake`로 전역 유일 64비트 `ID`를 조회 없이 발급하고 `base-62`로 인코딩한다. 충돌 확인이 없어 burst에 강하다. 최대 약 11자로 길고 시간순 키가 노출되지만, 현재는 공개 공유 링크라 이 위험을 허용한다.

야구보구는 이미 7장에서 `Snowflake ID 생성기`를 운영한다. 그래서 단축 키를 Snowflake ID의 base-62 인코딩으로 정하면 충돌 처리 로직과 충돌 확인 조회가 사라져 write burst를 받아낼 수 있다. 

> 순수 신규 설계라면 KGS를 먼저 검토하는 게 좋다. 여기서는 기존 Snowflake를 재사용해 충돌 확인 조회를 없애는 이점이 더 크다. 순차 키 수집이 실제 문제로 나타날 때만 keyed permutation을 추가한다.
> 

### 리다이렉션: 302와 Edge serving

- **선택: `302 Redirect`를 사용하고, 인기 링크는 `Edge/CDN`에서 캐싱해 응답한다.**
- **선택 이유:** 브라우저의 장기 캐싱은 피하면서 클릭 요청을 계속 관찰하고, 동시에 Edge에서 리다이렉션을 처리해 Origin 부하와 지연을 줄이기 위해서이다.
- **대안 비교:**
    - `301`: 브라우저에 영구적으로 캐싱될 수 있어 서버나 Edge까지 요청이 오지 않으므로 클릭 분석이 어려워진다.
    - `302`를 매번 Origin에서 처리: 클릭 분석은 가능하지만, 바이럴 시 모든 요청이 Origin으로 몰려 read 부하가 커진다.
- **보완:** `302` 응답에 적절한 `Cache-Control`을 적용해 Edge에서는 캐싱하고, 클릭 데이터는 **Edge access log/event → MQ → Analytics**로 비동기 수집한다.

### API

```jsx
POST /shorten            { longUrl }          -> { shortUrl }   // 내부 도메인 allowlist 검증
GET  /{shortKey}         -> 302 Location: target_url
GET  /{shortKey}/stats   -> 클릭 통계 (관리/대시보드)
```

### 데이터 모델

분석용 메타데이터는 분리해서 hot path와 캐시를 가볍게 유지한다.

```jsx
RedirectMapping (hot path)      ShareMetadata (분석용)
- short_key (PK)                - short_key
- target_url                    - owner_id
- created_at                    - kind (attendance/winrate/rank)
                                - team, game_id, season
```

Cassandra 스키마(hot path)

```jsx
CREATE TABLE short_urls (
    short_key text PRIMARY KEY,
    target_url text,
    created_at timestamp,
    kind tinyint
);
```

### 주요 컴포넌트

- Shorten API (생성, allowlist 검증) / Redirect API (stateless)
- Snowflake ID 생성기 (7장 재사용, 내장 라이브러리)
- Edge / CDN (매핑 캐시 조회, 인기 링크 302 직접 응답, access log 수집)
- 3계층 캐시: Edge, 애플리케이션 로컬, Redis
- Cassandra (source of truth, RF=3)
- Edge log에서 MQ로 흐르는 클릭 이벤트와 Analytics Worker (6장 파이프라인 재사용)
- Rate Limiter와 WAF (4장 재사용)
- Observability

## 개략적 추정

#### 클릭(read) 부하

공유 1건당 20에서 50 클릭, 하루 신규 500만 공유면 1억에서 2.5억 클릭수로 예상 가능하다.

인기 경기 종료 직후 60%가 30분에 몰리면

```jsx
250,000,000 x 0.6 / 1,800초 ≈ 83,000 QPS (평균 Peak)
바이럴 시 3배 ≈ 200,000~250,000 QPS
```

캐시 적중률 95% 이상을 목표로 하면 원본 저장소에 닿는 요청은 5% 이하로 떨어질 수 있다.

#### 단축 생성(write) 부하

```jsx
평균     : 5,000,000 / 86,400 ≈ 58 writes/s
경기 집중 : 5,000,000 x 0.6 / 1,800 ≈ 1,700 QPS
capacity : 예상 peak의 5~10배인 10,000~20,000 QPS까지 버티게 설계 (stress target)
```

Snowflake 발급은 조회 없는 in-memory 연산이라 이 정도 burst는 무리 없이 버틸 수 있다.

#### 저장 용량

```jsx
10년 100억 건 x 약 500B ≈ 5TB raw
RF=3 -> 약 15TB
+ index, SSTable overhead, compaction 여유, backup -> 수십 TB급
redirect 레코드를 좁히면 hot table 자체는 훨씬 작다
```

- Go deeper
    - 가장 중요한 흐름: 경기 종료 후 공유 링크 클릭 폭증
    - 먼저 생길 병목: 리다이렉션 read QPS, 인기 링크 Hot Key
    - 단일 장애 지점: 캐시 계층, 원본 저장소
    - 읽기 확장: 3계층 캐시(Edge, 로컬, Redis), 복제
    - 쓰기 확장: Shorten API와 Snowflake 노드 수평 확장
    - 주요 실패: 캐시 미스 폭주(cache stampede), Hot Key, 봇 클릭, 존재하지 않는 키 스캔

## 3. 핵심 설계 결정 (Decision Log)

- Decision #1: **Short Key는 Snowflake ID를 Base62로 인코딩한다**
    
    > 아래 그림의 가역 순열은 기본 경로가 아니다. 유효 링크를 연속 수집하는 문제가 실제로 확인될 때만 적용하는 선택 사항이다.
    
<img width="1600" height="900" alt="image" src="https://github.com/user-attachments/assets/fe0f06a4-e310-4875-8752-838a6f35a6fc" />
    
  - **해결하려는 문제**
      - 경기 종료 직후 단축 링크 생성이 몰릴 때 키 충돌 확인 조회가 병목이 될 수 있다.
      - 충돌이 발생했을 때 재시도하는 로직도 함께 관리해야 한다.
  - **선택 이유**
      - 7장에서 사용한 `Snowflake`는 DB 조회 없이 전역에서 유일한 ID를 만든다.
      - 기존 ID 발급 방식을 재사용하므로 URL 단축 전용 키 발급 시스템을 추가하지 않아도 된다.
      - 발급한 숫자 ID는 Base62로 바로 인코딩해 `short_key`로 사용한다.
  - **대안**
      - **KGS(Key Generation Service)**: 짧은 랜덤 키를 미리 만들어두고 발급할 때 하나씩 꺼낸다. 키를 6~8자로 유지하기 좋지만 키 풀을 별도로 운영해야 한다.
      - **Hash**: 긴 URL의 해시 일부를 키로 사용한다. 구현은 단순하지만 짧게 자르면 충돌 확인과 재시도가 필요하다.
      - **DB Auto Increment / Ticket Server**: 유일한 숫자 ID를 만들 수 있지만 중앙 발급 지점에 의존한다.
  - **트레이드오프**
      - 64비트 Snowflake ID는 Base62로 표현해도 최대 약 11자가 필요하다. `ygb.gg`처럼 짧은 도메인으로 전체 길이를 줄인다.
      - 키가 시간순으로 발급되므로 인접한 유효 키를 추측할 수 있다. 현재 링크는 SNS에 공개하는 콘텐츠이고 링크 자체가 접근 권한은 아니므로 이 위험을 받아들인다.
  - **재검토 조건**
      - 실제로 유효 링크를 연속 수집하는 문제가 발생하면 keyed permutation을 보조 방어로 검토한다. 이 방식은 인증을 대신하지 않으며 비밀 키 보관과 버전 관리 비용이 생긴다.
      - 비공개 공유처럼 링크 자체가 접근 권한이 되면 Snowflake 키를 쓰지 않고 96~128비트 랜덤 토큰과 권한 검사를 적용한다.

- Decision #2: **Storage = Cassandra를 Source of Truth로 사용**
    
<img width="267" height="150" alt="image" src="https://github.com/user-attachments/assets/9044450b-bbc8-46a2-9c28-3f7e38e59442" />
    
  - **해결하려는 문제**
      - 대부분의 요청이 `short_key → target_url` 단건 조회다.
      - UPDATE, JOIN, range scan 같은 복잡한 쿼리는 거의 필요하지 않고, 데이터가 계속 쌓이기 때문에 저장소를 수평으로 확장할 수 있어야 한다.
  - **선택 이유**
      - `short_key`를 partition key로 두면 해시 결과에 따라 데이터가 Cassandra ring 전체에 분산되고, 조회할 때도 해당 partition을 가진 replica만 찾으면 된다. (해시 함수로 token 계산해 해당 node의 replica 선택)
      - 단건 조회와 수평 확장이 중요한 현재 접근 패턴에 잘 맞는다.
      - (6장에서 이미 Cassandra를 사용하고 있기 때문에 새로운 저장소를 추가로 운영하지 않아도 된다.)
  - **대안**
      - **MySQL + Sharding**: 충분히 구현 가능하다. 다만 데이터가 커지면 `short_key`를 기준으로 shard를 나누고, 어떤 shard로 요청을 보낼지 routing하거나 resharding하는 부분을 별도로 관리해야 한다.
      - 현재는 관계형 모델의 JOIN이나 트랜잭션이 필요한 데이터가 아니어서 이 복잡도를 감수할 이유가 크지 않다고 판단했다.
  - **트레이드오프**
      - JOIN이나 자유로운 조건 검색, range scan에는 적합하지 않다.
      - 대신 현재 URL mapping은 `short_key` 단건 조회가 대부분이라 이 기능들을 포기해도 문제가 없다.
  - **재검토 조건**
      - vanity URL 검색이나 사용자별 링크 조회처럼 `short_key` 이외의 조건으로 조회해야 하는 요구사항이 늘어나면 별도의 인덱스나 조회용 저장소를 추가한다.
  
- Decision #3: Consistency = **Cassandra 저장이 확인된 뒤 Short URL을 반환**
    
<img width="267" height="150" alt="image" src="https://github.com/user-attachments/assets/4528122d-506c-42b6-9f68-957efda872a1" />
    
  - **해결하려는 문제**
      - 생성 API가 성공을 반환한 링크는 바로 클릭해도 정상적으로 동작해야 한다.
          - 캐시 장애 여부와 관계없이 `read-after-write`를 보장해야 한다.
  - **선택 이유**
      - 링크 생성은 `(1) Snowflake ID 생성 → (2) Base62 변환 → (3) Cassandra 저장 → (4) 저장 성공 확인 후 Short URL 반환` 순서로 처리한다.
      - Cassandra는 `RF=3`, write는 `LOCAL_QUORUM`을 사용해 같은 리전의 replica 과반에 저장된 것이 확인된 뒤 성공을 반환한다.
      - 생성 직후처럼 최신 데이터 확인이 필요한 read도 `LOCAL_QUORUM`을 사용하면 write quorum과 read quorum이 겹치기 때문에 acknowledged write를 읽을 수 있다.
          - R + W > RF(복제 계수)
      - Redis와 로컬 캐시는 성능을 위한 계층일 뿐 정합성을 보장하는 저장소가 아니다. 따라서 캐시 선채움은 `best-effort`로 처리하고, 실패해도 Cassandra 저장이 성공했다면 링크 생성은 성공시킨다.
  - **대안**
      - **캐시 선채움에 의존**: 생성과 동시에 Redis에 저장하면 대부분의 첫 조회는 빠르게 처리할 수 있지만, Redis 장애나 populate 실패가 발생할 수 있어 `read-after-write`을 제공할 수 없다.
  - **트레이드오프**
      - 생성 API가 Cassandra의 `LOCAL_QUORUM` 응답을 기다려야 하므로 가장 빠른 단일 replica write보다 **write latency가 증가**한다.
      - 대신 링크를 반환했다면 이후 조회할 수 있다는 보장을 우선한다.
  - **재검토 조건**
      - write latency가 실제 SLO를 만족하지 못하거나 Multi-Region으로 확장한다면 consistency level과 글로벌 `read-after-write` 범위를 다시 검토한다.
      
- Decision #4: Redirect = `302` + Edge serving
    
<img width="267" height="150" alt="image" src="https://github.com/user-attachments/assets/93028e1b-6e32-4411-8806-edd338829c46" />
  
  ```java
  전체 URL
  ──────────────────────────
  Cassandra
  수십억 개 전체 원본
  
            ↑
  
  Redis
  Origin에서 최근/자주 조회된 URL
  
            ↑
  
  Local Cache
  특정 API 인스턴스에서
  최근/자주 조회된 URL
  
            ↑
  
  Edge Cache
  특정 지역에서 최근/자주
  클릭된 URL
  ```
  
  - **해결하려는 문제**
      - 경기 종료 직후 몰리는 클릭을 빠르게 처리하면서도, 팀·경기·지역별 클릭 데이터를 수집해야 한다.
  - **선택 이유**
      - 리다이렉션은 `302`를 사용해 브라우저에 영구적으로 캐싱되는 것을 피한다.
      - 그렇다고 모든 요청을 Origin까지 보내지는 않는다. 인기 링크의 `302` 응답은 `Edge/CDN`에 캐싱해 사용자와 가까운 곳에서 바로 처리한다.
      - **Edge에서 처리된 요청도 access log나 이벤트로 남겨 비동기 분석 파이프라인으로 전달**한다. 덕분에 Origin 부하를 줄이면서 클릭 데이터도 수집할 수 있다.
  - **대안**
      - **`301` Redirect**: 브라우저에 장기간 캐싱될 수 있어 서버나 Edge까지 요청이 오지 않게 되면 클릭 데이터를 수집하기 어렵다.
      - **`302` + 모든 요청을 Origin에서 처리**: 클릭 데이터는 수집하기 쉽지만, 바이럴 트래픽까지 Origin이 모두 받아야 해서 read 부하가 커진다.
  - **트레이드오프**
      - Edge에서도 `302`를 캐싱할 수 있도록 `Cache-Control` 정책을 관리해야 한다.
      - 클릭 분석을 위해 Edge access log/event를 수집하는 파이프라인도 운영해야 한다.
  - **재검토 조건**
      - 클릭 분석의 중요도가 낮아지면 일부 링크는 `301`이나 더 긴 캐시 정책을 적용해 트래픽을 더 줄일 수 있다.
      - Edge 로그의 비용이나 지연이 커지면 링크 종류에 따라 Origin에서 수집할 데이터와 Edge에서 수집할 데이터를 나눈다.
   
- Decision #5: **Caching = `Edge` → `Local` → `Redis` 3계층**
    
<img width="267" height="150" alt="image" src="https://github.com/user-attachments/assets/6cf7a413-858c-42c8-99e7-41c1fa9fbef6" />
  
  ```java
  Client
  200,000 QPS
       ↓
  
  Edge
  99% HIT
       ↓
  2,000 QPS
  
  Local
  50% HIT
       ↓
  1,000 QPS
  
  Redis
  95% HIT
       ↓
  50 QPS
  
  Cassandra
  50 QPS
  ```
  
  - **해결하려는 문제**
      - 경기 종료 직후 수십만 QPS까지 몰릴 수 있는 클릭을 `Cassandra`가 직접 받지 않도록 한다.
      - 특히 하나의 인기 링크에 요청이 집중되는 Hot Key도 `Origin`까지 최대한 내려오지 않게 해야 한다.
  - **선택 이유**
      - **Edge/CDN**에서 특정 지역의 인기 URL을 먼저 처리해 대부분의 요청을 Origin까지 보내지 않는다.
      - Edge에서 처리하지 못한 요청은 **`Local Cache`**에서 확인해 Redis로 가는 network hop을 줄인다.
      - **`Redis`**는 여러 API 인스턴스가 함께 사용하는 hot set을 저장해 Cassandra 조회를 줄인다.
      - URL 매핑은 생성 후 수정하지 않기 때문에 캐시된 값이 오래되어 잘못된 값을 반환하는 문제가 거의 없다. 따라서 복잡한 cache invalidation 없이 TTL을 메모리 관리 목적으로 사용할 수 있다.
      - 존재하지 않는 `short_key`도 짧게 `negative caching`해 반복적인 invalid key 요청이 Cassandra까지 내려가는 것을 막는다.
  - **대안**
      - **Redis 단일 계층**: 구조는 단순하지만 모든 Edge miss가 Origin과 Redis까지 들어오므로 바이럴 트래픽을 충분히 앞단에서 흡수하지 못한다.
      - **Edge + Cassandra**: Origin의 Redis 운영은 줄일 수 있지만 Edge miss가 발생할 때마다 Cassandra를 직접 조회해야 한다.
  - **트레이드오프**
      - Edge, Local, Redis까지 여러 캐시 계층의 용량과 TTL 정책을 각각 관리해야 한다.
      - Local Cache는 API 인스턴스마다 별도로 존재하기 때문에 같은 데이터가 중복 저장될 수 있다.
      - Edge 캐시와 로그 파이프라인까지 포함하면 운영 복잡도와 비용이 증가한다.
  - **재검토 조건**
      - 실제 Edge hit ratio가 충분히 높아 Local Cache나 Redis가 큰 효과를 내지 못한다면 캐시 계층을 단순화한다.
      - 반대로 Edge miss 이후 Cassandra 부하가 예상보다 크다면 Redis 용량과 TTL, hot set 정책을 조정한다.
   

- Decision #6: **Hot Key / Cache Stampede = 복제 + Single-flight + Stale Serving**
    
<img width="267" height="150" alt="image" src="https://github.com/user-attachments/assets/7a2cc53e-c996-4473-9316-7d12d142fffb" />
  
  - **해결하려는 문제**
      - **Hot Key**: 인기 있는 하나의 `short_key`에 요청이 몰려 특정 Redis shard가 병목이 되는 문제다.
      - **Cache Stampede**: 인기 키의 캐시가 만료되는 순간 여러 요청이 동시에 miss가 나면서 Cassandra로 한꺼번에 내려가는 문제다.
  - **선택 이유**
      - **Hot Key**는 Edge와 각 API 서버의 Local Cache에 인기 데이터를 복제해 최대한 앞단에서 처리한다. 하나의 Redis shard가 인기 링크의 전체 트래픽을 받지 않도록 한다.
      - **Cache Stampede**는 `single-flight`를 적용해 같은 키에 대한 동시 miss 중 하나만 Cassandra를 조회하고, 나머지는 그 결과를 기다려 공유한다.
      - 여러 인기 키가 동시에 만료되는 것을 줄이기 위해 TTL에 작은 랜덤 값(`jitter`)을 추가한다.
      - URL 매핑은 생성 후 바뀌지 않으므로 캐시가 만료됐더라도 기존 값을 안전하게 사용할 수 있다. `stale-while-revalidate`로 기존 값을 응답하면서 뒤에서 갱신하고, 원본 장애 시에는 `stale-if-error`로 만료된 값을 계속 제공할 수 있다.
  - **대안**
      - **Redis 확장만으로 대응**: 전체 처리량은 늘릴 수 있지만 하나의 Hot Key가 특정 shard에 집중되는 문제는 그대로 남을 수 있다.
      - **TTL만 길게 설정**: miss 빈도는 줄지만 언젠가 만료되는 순간의 동시 요청 문제 자체는 해결하지 못한다.
  - **트레이드오프**
      - `single-flight`는 기본적으로 API 프로세스 내부에서만 동작한다. API 서버가 100대라면 같은 순간 최대 100개의 원본 조회가 발생할 수 있다. (최대 요청 수 제한)
      - 다만 10만 개의 요청이 그대로 Cassandra에 도달하는 것보다 최대 수십~수백 건으로 줄이는 것만으로도 충분한 보호 효과를 얻을 수 있다.
      - Stale serving과 TTL jitter까지 추가하면서 캐시 정책이 복잡해진다.
  - **재검토 조건**
      - 프로세스별 `single-flight`만으로도 Cassandra에 부담이 크다면 Redis 기반 분산 락 등으로 요청 병합 범위를 여러 인스턴스로 확장하는 방식을 검토한다.
   
- Decision #7: **Analytics(분석) = redirect hot path와 분리, Edge log -> MQ**
    
<img width="267" height="150" alt="image" src="https://github.com/user-attachments/assets/cd525646-fabd-4526-bcd0-c242e067a174" />
  
  - **해결하려는 문제**
      - 클릭 데이터를 최대한 누락하지 않으면서 분석 때문에 리다이렉션이 느려지지 않도록 한다.
      - 인기 링크는 Edge에서 바로 응답하므로 Origin에서만 이벤트를 수집하면 Edge hit에 해당하는 클릭을 놓칠 수 있다.
  - **선택 이유**
      - 모든 클릭이 먼저 거치는 Edge에서 `short_key`, timestamp, region, User-Agent, referrer 등을 **비동기로 수집**한다.
      - Edge access log/event를 `MQ`로 전달하고, Analytics Worker가 `short_key`에 해당하는 경기·팀 정보를 결합해 팀·경기·지역별 유입을 집계한다.
      - SNS `preview bot`과 실제 사용자 구분도 리다이렉션 경로가 아니라 분석 단계에서 처리한다.
      - 분석 파이프라인을 serving path와 분리했기 때문에 MQ나 Worker에 장애가 발생해도 리다이렉션에는 영향을 주지 않는다.
      - 분석 이벤트는 `at-least-once` 전달을 전제로 한다. 중복 이벤트가 들어와도 결과가 달라지지 않도록 집계 단계에서 멱등성을 고려한다.
  - **대안**
      - **Redirect API에서 직접 이벤트 발행**: 구현은 단순하지만 Edge에서 처리된 클릭을 볼 수 없다. 이벤트 발행 로직이 redirect hot path에 들어간다.
      - **모든 요청을 Origin으로 전달**: 클릭을 한 곳에서 수집하기 쉽지만 분석을 위해 Edge serving의 장점을 포기하게 된다.
  - **트레이드오프**
      - 클릭 데이터는 실시간으로 바로 반영되지 않고 수초~수분 정도 늦게 집계될 수 있다.
      - Edge 로그 수집과 MQ, Worker까지 별도의 분석 파이프라인을 운영해야 한다.
      - 클릭 분석은 과금 데이터가 아니므로 일부 중복이나 미세한 유실은 허용한다.
  - **재검토 조건**
      - 클릭 데이터가 과금이나 정산처럼 정확성이 중요한 데이터로 사용되기 시작하면 이벤트 전달과 중복 제거에 대한 보장을 더 강하게 가져간다.
   

- Decision #8: **Abuse = Destination Allowlist + 생성 Rate Limit + Redirect는 Edge/WAF에서 방어**
    
<img width="267" height="150" alt="image" src="https://github.com/user-attachments/assets/5e67abc0-6701-4196-a3f4-87bbf3edbb39" />
  
  - **해결하려는 문제**
      - 임의의 외부 URL을 단축할 수 있게 두면 `ygb.gg`가 피싱이나 악성 사이트로 보내는 **Open Redirect**로 악용될 수 있다.
      - 생성 API를 대량 호출해 불필요한 URL 매핑을 계속 저장하거나, 존재하지 않는 `short_key`를 반복 조회해 원본 저장소에 부하를 줄 수 있다.
  - **선택 이유**
      - **Destination Allowlist**: 야구보구 내부 딥링크와 승인된 웹 도메인만 단축할 수 있도록 제한한다. 외부 도메인과 `javascript:`, `data:`, `file:` 같은 scheme은 허용하지 않는다.
      - **생성 API(post)**: 호출할 때마다 영구 데이터가 생기므로 사용자와 IP 기준으로 비교적 강하게 Rate Limit을 적용한다.
      - **Redirect API**: 정상적인 바이럴 트래픽도 조회량이 매우 클 수 있으므로 application-level Rate Limit을 강하게 적용하지 않는다. 대규모 공격이나 비정상 요청은 최대한 Edge/WAF에서 먼저 차단한다.
      - **Invalid Key Scan**: 존재하지 않는 `short_key`는 짧게 negative caching해 같은 요청이 반복해서 Cassandra까지 내려가지 않도록 한다.
      - SNS preview bot은 정상적인 링크 미리보기에도 필요하므로 serving 단계에서 일괄 차단하지 않고 분석 단계에서 별도로 분류한다.
  - **대안**
      - **모든 URL 허용**: 범용 URL Shortener로 사용할 수 있지만 피싱이나 악성 URL에 서비스 도메인이 악용될 수 있다.
      - **Redirect에도 강한 Rate Limit 적용**: 공격 방어는 쉬워지지만 정상적인 바이럴 트래픽까지 차단할 가능성이 있다.
  - **트레이드오프**
      - 새로운 내부 도메인이나 딥링크가 추가될 때 allowlist를 관리해야 한다.
      - 생성 Rate Limit을 너무 낮게 잡으면 경기 종료 직후 정상적인 공유 요청까지 차단할 수 있어 임계값 조정이 필요하다.
      - Edge/WAF 정책 역시 정상적인 크롤러나 SNS preview 요청을 공격으로 오인하지 않도록 관리해야 한다.
  - **재검토 조건**
      - 외부 URL 단축 기능이 필요해진다면 단순 allowlist 대신 URL reputation 검사, abuse detection 등의 별도 안전장치를 검토한다.
        - 공격 패턴이나 정상 트래픽 규모가 바뀌면 생성 Rate Limit과 WAF 정책을 다시 조정한다.
       
- Decision #9: **Durability = Replication + Repair + Backup**
    
<img width="1600" height="900" alt="image" src="https://github.com/user-attachments/assets/7ac20298-42c6-4eed-af94-28bdc44d1783" />
    
  - **해결하려는 문제**
      - 한 번 생성되어 외부에 공유된 URL 매핑은 노드 장애나 데이터 손상이 발생해도 유실되지 않아야 한다.
  - **선택 이유**
      - Cassandra는 `RF=3`으로 구성해 하나의 매핑을 여러 replica에 저장한다. `LOCAL_QUORUM` write가 성공한 뒤에만 생성 성공을 반환해 단일 replica 장애가 발생해도 데이터를 유지할 수 있도록 한다.
      - replica 일부가 일시적인 장애 등으로 write를 놓쳐 서로 다른 상태가 될 수 있으므로 정기적인 `repair`를 통해 replica 간 데이터를 맞춘다.
      - Replication과 repair만으로는 잘못된 삭제나 데이터 손상까지 복구할 수 없다. 이런 장애에 대비해 `snapshot/backup`을 별도의 장애 도메인에 보관한다.
  - **대안**
      - **Replication만 사용**: 노드 장애에는 대응할 수 있지만 잘못된 삭제나 데이터 손상도 replica에 전파되므로 과거 상태로 복구할 수 없다.
      - **Backup만 사용**: 데이터 복구는 가능하지만 노드 장애가 발생할 때 즉시 다른 replica에서 서비스를 이어갈 수 없다.
  - **트레이드오프**
      - RF=3만큼 저장 공간이 늘어나고, quorum write로 인해 단일 replica write보다 latency가 증가한다.
      - repair와 snapshot/backup을 별도로 운영해야 하므로 저장 비용과 운영 복잡도가 생긴다.
  - **재검토 조건**
      - Multi-Region으로 확장하면 리전 전체 장애까지 고려해 replication 범위와 consistency level, 리전 외 backup 정책을 다시 설계한다.
   
- Decision #10 (향후): **Future Evolution = Multi-Region, Link TTL, Vanity URL은 필요할 때 도입**
    
<img width="267" height="150" alt="image" src="https://github.com/user-attachments/assets/48f10e69-15eb-4456-a68c-1f1e58465c85" />
    
  - **해결하려는 문제**
      - 해외 트래픽 증가, 임시 링크, 커스텀 URL처럼 현재 요구사항에는 없지만 서비스가 커지면서 생길 수 있는 요구사항이 있다.
      - 처음부터 모두 구현하면 운영 복잡도만 늘어나므로 도입 시점을 정해둔다.
  - **선택 이유**
      - **Multi-Region**: 현재는 Edge/CDN + 단일 Origin Region으로 처리한다. 해외 사용자의 Edge miss latency가 SLO를 넘거나 리전 장애 대응이 중요해지면 여러 Region에서 redirect를 처리하도록 확장한다.
      - **Link TTL**: SNS에 공유된 링크는 오래된 게시물에서도 다시 클릭될 수 있으므로 기본적으로 만료시키지 않는다. 이벤트나 프로모션처럼 수명이 정해진 링크가 생기면 링크 단위 TTL을 추가한다.
      - **Vanity URL**: 현재는 시스템이 `short_key`를 자동 생성한다. `ygb.gg/kia`처럼 사람이 지정하는 주소가 필요해지면 충돌 검사, 예약어 관리 등을 포함한 별도 발급 경로를 추가한다.
      - **Deep Link Fallback**: 앱이 설치되지 않은 사용자를 웹이나 앱스토어로 보내야 하는 요구가 생기면 redirect 이후의 fallback routing을 추가한다.
  - **대안**
      - 처음부터 Multi-Region, TTL, Vanity URL을 모두 지원할 수 있지만 현재 필요하지 않은 데이터 복제, 충돌 관리, 만료 정책까지 운영해야 한다.
  - **트레이드오프**
      - 현재 구조는 단순하지만 새로운 요구사항이 생기면 그 시점에 저장 구조나 routing을 확장해야 한다.
      - 특히 Multi-Region에서는 생성 직후 다른 Region에서도 바로 조회되어야 하는지 등 consistency 정책을 추가로 결정해야 한다.
  - **재검토 조건**
      - 해외 Edge miss의 p99 latency가 SLO를 지속적으로 넘거나 Region 장애가 redirect 가용성에 영향을 주면 **Multi-Region**을 검토한다.
      - 이벤트·프로모션처럼 일정 기간 후 사라져도 되는 링크가 생기면 **Link TTL**을 도입한다.
      - 공식 마케팅이나 브랜딩을 위해 사람이 지정하는 주소가 필요해지면 **Vanity URL**을 도입한다.
      - 앱 미설치 사용자의 이탈이 문제가 되면 **Deep Link Fallback**을 추가한다.

## 4. 상세 설계

링크 생성 경로는 초당 수천 건이고, 리다이렉션 경로는 수십만 건까지 올라간다. 그래서 두 경로를 같은 방식으로 확장하지 않는다. 생성에서는 충돌 확인 조회를 없애고 성공한 매핑의 내구성을 보장한다. 조회에서는 불변 매핑을 Edge까지 캐시해 Cassandra에 도달하는 요청을 줄인다.

아래에서는 키가 만들어지는 과정, 캐시 미스가 원본까지 전달되는 과정, 생성 직후 조회의 정합성, 남용과 장애 대응 순서로 살펴본다.

### base-62 인코딩과 키 예측 가능성

> 아래 그림에서 가역 순열 단계는 선택 사항이다. 현재 기본 경로는 `Snowflake ID → Base62`다.
> 

!ygb-04-base62-v3.svg

Snowflake가 만든 64비트 ID를 Base62로 바로 인코딩한다.

`Snowflake ID → Base62 → short_key`

Base62는 숫자의 표현만 바꾼다. ID의 정보량이 줄어드는 것은 아니므로 64비트 전체를 표현하면 최대 길이는 `ceil(log62(2^64))`, 약 11자다.

Snowflake ID는 시간순으로 발급되기 때문에 앞뒤 키를 추측할 수 있다. 하지만 현재 링크는 SNS에 공개하는 카드와 기록을 가리키며, 링크 자체가 접근 권한 역할을 하지 않는다. 기본 경로에 가역 순열을 넣어 키 관리와 회전 문제를 추가하기보다 Edge/WAF에서 연속 조회 패턴을 감시하고 비정상적인 IP나 ASN을 제한한다.

유효 링크 대량 수집이 실제 문제로 확인되면 keyed permutation을 추가할 수 있다. 이 방법은 열거 비용을 높이는 보조 수단일 뿐 인증이나 기밀성을 제공하지 않는다. 비공개 공유 기능에는 충분히 긴 랜덤 토큰과 권한 검사를 별도로 사용한다.

### 캐시 3계층과 miss 대응

!ygb-03-cache-tiers-v3.svg

조회 순서는 Edge/CDN, 애플리케이션 로컬 캐시, Redis, Cassandra다. 앞 계층에서 값을 찾으면 뒤 계층은 호출하지 않는다. Cassandra에서 찾은 매핑은 Redis와 로컬 캐시에 채워 다음 요청부터 재사용한다.

같은 키가 한꺼번에 캐시 미스가 나면 `single-flight`로 원본 조회를 합친다.

```go
v, err, _ := group.Do(shortKey, func() (any, error) {
    if v, ok := redis.Get(shortKey); ok {
        return v, nil
    }

    v, err := cassandra.Get(shortKey)
    if err != nil {
        return nil, err
    }

    redis.Set(shortKey, v) // 캐시 저장 실패는 조회 결과에 영향을 주지 않는다.
    return v, nil
})
```

한 인스턴스에 `abc123` 요청 1,000건이 동시에 들어와도 Cassandra 조회는 한 건으로 줄어든다. 다만 이 묶음은 프로세스 안에서만 유효하다. 서버가 100대라면 같은 순간에 최대 100건이 원본으로 갈 수 있다. 분산 락을 추가해 완전히 한 건으로 만드는 것보다, 이 정도로 부하를 줄이고 구조를 단순하게 유지하는 편을 택한다.

존재하지 않는 키도 10~60초 동안 짧게 캐시한다. 스캐너가 임의의 키를 반복해서 요청해도 매번 Cassandra까지 내려가지 않게 하기 위해서다.

### read-after-write 보장

생성 API는 Cassandra 쓰기가 끝나기 전에 short URL을 반환하지 않는다. 처리 순서는 다음과 같다.

1. Snowflake ID를 발급하고 Base62로 인코딩한다.
2. Cassandra에 매핑을 저장하고 `LOCAL_QUORUM` 응답을 기다린다.
3. 쓰기가 성공하면 short URL을 반환한다.
4. Redis와 Edge 캐시는 best-effort로 채운다.

RF=3에서 쓰기와 읽기를 모두 `LOCAL_QUORUM`으로 처리하면 쓰기에 참여한 복제본과 읽기에 참여한 복제본이 최소 하나 겹친다. 같은 리전에서 생성 직후 조회해도 방금 저장한 매핑을 읽을 수 있다.

캐시 선채움은 첫 조회를 빠르게 만드는 최적화다. 캐시 저장이 실패해도 Cassandra 쓰기가 완료됐다면 생성 요청은 성공으로 처리한다.

### 남용 방어

단축 생성과 리다이렉션은 트래픽 성격이 달라 같은 제한을 걸지 않는다.

- 단축 생성: URL을 파싱한 뒤 scheme과 host를 정확히 비교한다. `https://yagubogu.app/...`와 `yagubogu://...`만 허용하고, 외부 도메인과 `javascript:`, `data:`, `file:`은 거부한다. 문자열 prefix 비교만 사용하면 `yagubogu.app.attacker.com` 같은 주소를 놓칠 수 있다.
- 생성 요청 제한: 로그인 사용자는 사용자 ID, 비로그인 요청은 IP를 기준으로 제한한다. 정상적인 공유 생성보다 훨씬 높은 반복 호출을 먼저 차단한다.
- 리다이렉션: 경기 종료 직후의 정상 바이럴 트래픽을 공격으로 오인하지 않도록 강한 사용자별 제한을 두지 않는다. WAF와 DDoS 방어로 비정상 패턴을 걸러내고 Edge가 대부분의 요청을 처리한다. 유효 키를 순서대로 훑는 요청은 IP·ASN·키 접근 패턴을 함께 보고 별도로 제한한다.
- 클릭 분석: SNS 미리보기 봇과 검색 크롤러는 리다이렉션 단계에서 막지 않는다. User-Agent와 알려진 봇 대역을 이용해 분석 파이프라인에서 사람의 클릭과 분리한다.

### 장애 시 동작

#### Redis가 응답하지 않을 때

로컬 캐시 다음 단계에서 Cassandra로 바로 내려간다. 요청 지연과 원본 QPS는 늘지만 리다이렉션은 계속 제공한다. `single-flight`가 같은 키의 동시 조회를 묶어 Cassandra의 순간 부하를 줄인다.

#### Cassandra를 읽을 수 없을 때

Edge, 로컬, Redis에 남아 있는 매핑은 계속 302로 응답한다. 매핑이 불변이므로 만료된 캐시도 `stale-if-error` 정책으로 잠시 사용할 수 있다. 캐시에 없던 링크는 원본이 복구될 때까지 실패한다.

#### 클릭 분석이 밀릴 때

리다이렉션 응답과 클릭 이벤트 처리는 분리되어 있다. MQ에 이벤트를 쌓고 소비자를 늘리거나 나중에 재처리한다. 분석 지연은 허용하지만 사용자 리다이렉션을 늦추지는 않는다.

#### Snowflake 발급이 멈출 때

새 단축 링크 생성만 실패한다. 이미 만들어진 링크의 조회 경로는 Snowflake를 사용하지 않으므로 계속 동작한다. 시계 역행과 worker ID 충돌은 7장의 발급기 정책을 따른다.

### 확장 방식

읽기 부하가 늘면 먼저 Edge 적중률과 인기 키 분산 상태를 확인한다. 캐시에 충분히 남아 있는데 특정 Redis shard가 뜨거우면 로컬 캐시와 Edge 복제를 늘린다. 전체 미스율이 높아 Cassandra QPS가 오르면 TTL과 워밍업 정책을 조정한다.

생성 부하는 stateless Shorten API와 Snowflake 노드를 늘려 대응한다. Cassandra는 `short_key` 파티션 키로 데이터를 분산하므로 노드를 추가해 저장 용량과 처리량을 함께 확장한다. 오래 조회되지 않은 링크는 콜드 스토리지로 옮기되, 첫 조회 시 복원되는 경로를 별도로 둔다.

## 5. 운영과 마무리

### 운영에서 먼저 볼 신호

리다이렉션 지연만 보고 있으면 원본 장애의 전조를 놓치기 쉽다. Edge 적중률이 떨어지는 순간 Redis와 Cassandra QPS가 함께 오르는지 확인한다. 특정 `short_key`에 요청이 몰리는 Hot Key와, 여러 키가 동시에 만료되는 Stampede도 다른 지표로 봐야 한다.

- 사용자 경로: 리다이렉션 p50/p95/p99, 302 성공률, 존재하지 않는 키 비율
- 캐시: Edge·로컬·Redis 적중률, 계층별 조회 시간, stale 응답 수
- 원본 저장소: Cassandra 읽기/쓰기 QPS, `LOCAL_QUORUM` 실패율, timeout
- 생성: 발급 QPS와 실패율, allowlist 거부율, 사용자·IP별 rate limit 차단율
- 분석: MQ lag, 재처리 건수, 봇으로 분류된 클릭 비율

### 알람을 받았을 때

캐시 적중률 하락과 Cassandra QPS 상승이 같이 나타나면 캐시 만료나 배포로 인한 cold start를 먼저 의심한다. 새 인스턴스는 한꺼번에 트래픽을 받지 않게 점진적으로 투입하고, 인기 링크를 먼저 워밍업한다.

한 키의 요청만 치솟으면 Hot Key다. Edge와 로컬 캐시에서 해당 키를 더 넓게 복제한다. TTL 경계에서 여러 요청이 동시에 원본으로 내려가면 Stampede이므로 `single-flight`, TTL jitter, stale serving이 실제로 적용됐는지 확인한다.

MQ lag만 증가하고 302 지연은 그대로라면 분석 소비자를 늘린다. 리다이렉션 경로까지 느려졌다면 두 파이프라인이 공유하는 CPU, 네트워크, 로그 전송 자원이 없는지 확인한다.

### 트래픽이 10배가 되면

노드를 바로 늘리기 전에 원본에 도달하는 비율부터 줄인다. 적용 순서는 다음과 같다.

1. Edge 캐싱 비중을 높이고 인기 링크를 미리 워밍업한다.
2. 사용자와 가까운 리전에 Edge·지역 캐시를 둔다.
3. 오래 조회되지 않은 링크를 콜드 스토리지로 분리한다.
4. 그래도 원본 QPS와 저장 용량이 부족하면 Redis와 Cassandra 노드를 늘린다.

### 남은 설계 과제

- 링크 만료 시 보여줄 화면과 앱 미설치 사용자의 웹·스토어 폴백
- vanity URL의 충돌 처리, 금칙어, 상표권 신고 절차
- SNS 미리보기용 Open Graph 응답과 캐시 정책
- 지역별 클릭 데이터를 관광 분석 파이프라인으로 넘길 때의 개인정보 최소화

- Edge / CDN
    - 고려할 때:
        - viral read 흡수, 리다이렉션을 사용자 근처에서 종료
    - 주의할 때:
        - 302 캐싱 정책(Cache-Control), 로그 파이프라인

        - 매핑 캐시 조회, 인기 링크 302 직접 응답, access log 수집

- Cache (Local + Redis)
    - 고려할 때:
        - read 폭증, 불변 매핑
    - 주의할 때:
        - Hot Key, Cache Stampede, 메모리
    - 정책:
        - read-through, 무효화 불필요, negative cache 짧은 TTL
    - Go deeper: single-flight, TTL jitter, 계층별 적중률
- Database (Cassandra, source of truth)
    - 고려할 때:

    - 고려할 때:

- Rate Limiter / WAF
    - 생성: allowlist + IP/사용자 강한 rate limit

    - Go deeper: 4장 처리율 제한 장치

## 🎤 면접 5분 스크립트

> 설명 순서: 요구사항과 트래픽 1분 → 키와 저장소 1분 → 리다이렉션과 캐시 2분 → 분석과 장애 대응 1분
> 
- 1) 문제와 트래픽 (60초)
    
    설계할 서비스는 야구보구의 공유 링크 단축기입니다. 사용자가 직관 기록이나 승률 카드를 공유하면 긴 딥링크를 짧게 만들고, 이 링크를 누른 사람을 원래 화면으로 보냅니다.
    
    트래픽은 경기 종료 직후에 몰립니다. 링크 생성도 순간적으로 늘지만, 공유된 링크를 누르는 요청은 그보다 20배 이상 많습니다. 바이럴이 생기면 리다이렉션이 초당 20만 건을 넘을 수 있어서 생성보다 조회 경로를 먼저 보호해야 합니다.
    
    여기서 활용할 수 있는 조건이 하나 있습니다. 한 번 만든 `short_key → target_url` 매핑은 바뀌지 않습니다. 이 값을 Edge까지 오래 캐시해 대량 조회가 원본 저장소로 내려오지 않게 하겠습니다.
    
- 2) 키 발급과 저장소 (60초)
    
    키 생성 방식으로 해시, KGS, Snowflake ID를 비교했습니다. 해시는 키를 짧게 만들기 쉽지만 충돌 확인을 위해 저장소 조회가 필요합니다. KGS도 좋은 선택이지만 별도 키 풀을 운영해야 합니다.
    
    이 서비스는 7장에서 만든 Snowflake 발급기를 이미 사용하고 있습니다. 그래서 Snowflake ID를 base-62로 바로 인코딩합니다. 발급 과정에 충돌 확인 조회가 없고 별도 키 풀도 운영하지 않아도 됩니다. 키가 시간순으로 노출되지만 현재 대상은 공개 공유 콘텐츠라 허용하고, 연속 수집이 실제 문제로 나타나면 keyed permutation을 보조 방어로 검토하겠습니다.
    
    저장소는 Cassandra를 선택했습니다. 조회가 `short_key` 기준 단건 읽기이고 JOIN이나 범위 검색이 필요하지 않기 때문입니다. `short_key`를 파티션 키로 두고 RF=3, `LOCAL_QUORUM`으로 저장합니다.
    
- 3) 리다이렉션과 캐시 (2분)
    
    리다이렉션은 302를 사용합니다. 다만 302라고 해서 매 요청을 Origin으로 보내지는 않습니다. `Cache-Control`을 명시해 인기 링크는 Edge/CDN에서 바로 302를 응답하고, 클릭 기록도 Edge access log에서 수집합니다.
    
    Edge에서 미스가 나면 Redirect API가 로컬 캐시, Redis, Cassandra 순으로 조회합니다. Cassandra에서 읽은 값은 앞 계층에 다시 채웁니다. 존재하지 않는 키도 짧게 negative cache에 넣어 무작위 키 스캔이 원본까지 내려가지 않게 합니다.
    
    Hot Key와 Cache Stampede는 구분해서 대응합니다. Hot Key는 값이 캐시에 있어도 한 키에 요청이 계속 몰리는 문제라 Edge와 로컬 캐시로 복제해 분산합니다. Stampede는 TTL이 끝난 순간 요청이 한꺼번에 원본으로 내려가는 문제라 `single-flight`, TTL jitter, stale serving을 사용합니다.
    
    생성 직후 조회는 캐시가 아니라 Cassandra로 보장합니다. 쓰기가 `LOCAL_QUORUM`으로 끝난 뒤에만 short URL을 반환하고, 캐시 선채움은 그 다음에 best-effort로 처리합니다.
    
- 4) 분석과 장애 대응 (60초)
    
    클릭 분석은 리다이렉션 경로에서 떼어냅니다. Edge 로그를 MQ로 보내고 worker가 팀, 경기, 지역 기준으로 집계합니다. 소비가 늦어져도 302 응답에는 영향을 주지 않습니다. SNS 미리보기 봇도 이 단계에서 따로 분류합니다.
    
    Redis가 멈추면 Cassandra로 폴백하되 `single-flight`로 원본을 보호합니다. Cassandra가 일시적으로 읽히지 않아도 캐시에 남은 불변 매핑은 `stale-if-error`로 계속 응답합니다. Snowflake 장애는 새 링크 생성에만 영향을 주고 기존 링크의 리다이렉션에는 영향을 주지 않습니다.
    
    정리하면, 불변 매핑을 Edge까지 캐시하고 리다이렉션과 분석을 분리해 경기 종료 직후의 읽기 폭증이 Cassandra까지 전달되지 않도록 설계했습니다.
    

## ❓ 예상 꼬리질문 Q&A

- Q. 302를 CDN에서 캐시하면 클릭 수를 놓치지 않나요?
    
    Origin 요청만 세면 놓칩니다. 그래서 클릭 집계 기준을 Origin access log가 아니라 Edge access log로 둡니다. Edge는 캐시된 302를 바로 응답하면서 요청 로그를 비동기로 남깁니다. 로그 유실이나 중복은 일부 허용하고, MQ 이후 집계는 멱등하게 처리합니다.
    
- Q. 301이 아니라 302를 선택한 이유는 무엇인가요?
    
    301은 브라우저가 오래 기억할 수 있어서 이후 클릭이 Edge에도 도달하지 않을 수 있습니다. 302에 명시적인 `Cache-Control`을 붙이면 Edge에서는 캐시하면서 브라우저의 장기 영구 캐시는 피할 수 있습니다. 링크 수정 기능이 없더라도 클릭 관측이 필요해 302를 선택했습니다.
    
- Q. 생성하자마자 링크를 눌러도 동작하나요?
    
    동작해야 합니다. Cassandra 쓰기가 `LOCAL_QUORUM`으로 완료된 뒤에만 생성 성공을 반환합니다. RF=3에서 읽기도 `LOCAL_QUORUM`으로 수행하면 읽기와 쓰기에 참여한 복제본이 겹치므로 같은 리전에서 생성 직후 값을 읽을 수 있습니다. Redis와 Edge 선채움은 지연을 줄이는 최적화일 뿐 성공 조건은 아닙니다.
    
- Q. 해시가 더 짧은데 Snowflake를 택한 이유는 무엇인가요?
    
    해시 앞부분만 쓰면 충돌 가능성이 있어 발급할 때마다 기존 키를 확인하거나 충돌 재시도 로직이 필요합니다. 경기 종료 직후 생성 요청이 몰릴 때 이 조회가 쓰기 경로의 병목이 됩니다. Snowflake는 조회 없이 유일한 ID를 만들 수 있고 기존 7장 인프라도 재사용할 수 있습니다. 대신 최대 약 11자로 길어지는 비용을 받아들였습니다.
    
- Q. 새로 만드는 서비스라면 그래도 Snowflake를 쓰나요?
    
    반드시 그렇지는 않습니다. 기존 발급기가 없다면 KGS를 먼저 비교하겠습니다. 미리 만든 짧은 키를 꺼내 쓰므로 충돌 확인 조회가 없고 키 길이도 짧게 유지할 수 있습니다. 이 설계에서 Snowflake를 선택한 가장 큰 이유는 이미 운영 중인 구성요소를 재사용할 수 있기 때문입니다.
    
- Q. MySQL을 샤딩해도 되는데 왜 Cassandra인가요?
    
    가능합니다. 다만 이 데이터의 주된 연산은 `short_key` 한 건 조회이고 UPDATE, JOIN, 범위 검색은 거의 없습니다. Cassandra는 이 접근 패턴을 파티션 키 조회로 처리하고 노드를 추가해 수평 확장하기 쉽습니다. 6장에서 이미 운영하고 있다는 점도 선택에 영향을 줬습니다. 복합 검색이나 관리 기능이 커지면 별도 인덱스나 RDB를 보조 저장소로 검토하겠습니다.
    
- Q. Hot Key와 Cache Stampede는 어떻게 구분하나요?
    
    Hot Key는 캐시가 정상이어도 특정 키의 QPS가 계속 높은 상태입니다. Edge와 로컬 캐시에 값을 복제해 한 Redis shard로 요청이 몰리지 않게 합니다.
    
    Stampede는 캐시가 만료된 짧은 순간에 같은 키의 미스가 동시에 발생하는 현상입니다. `single-flight`로 한 인스턴스의 조회를 합치고, TTL jitter로 만료 시점을 흩뜨리며, 원본 장애 때는 stale 값을 제공합니다.
    
- Q. single-flight를 써도 서버가 100대면 Cassandra에 100건이 가지 않나요?
    
    맞습니다. `single-flight`는 프로세스 단위라 최악에는 인스턴스 수만큼 원본 조회가 생깁니다. 그래도 10만 건이 그대로 내려가는 것보다 훨씬 작습니다. 전역 분산 락은 지연과 장애 지점을 추가하므로 먼저 로컬 결합과 Edge 캐시로 줄이고, 이 부하도 감당하기 어려울 때만 요청 합성 계층을 더하겠습니다.
    
- Q. 존재하지 않는 키를 계속 요청하면 어떻게 하나요?
    
    `NOT_FOUND` 결과를 10~60초 동안 negative cache에 저장합니다. `/a`, `/b`, `/c`처럼 임의 키를 스캔해도 같은 요청이 Cassandra까지 반복해서 내려가지 않습니다. 키 생성은 durable write가 끝난 뒤에만 성공하므로 짧은 negative TTL과 함께 사용하면 새 링크를 오래 가리는 문제도 제한할 수 있습니다.
    
- Q. 외부 URL도 단축할 수 있나요?
    
    지원하지 않습니다. URL을 파싱한 뒤 허용된 scheme과 host를 정확히 비교해 야구보구 딥링크와 승인된 웹 도메인만 받습니다. 단순 문자열 prefix 검사는 `yagubogu.app.attacker.com` 같은 우회 주소를 허용할 수 있으므로 사용하지 않습니다. 이 제한이 없으면 단축 도메인이 피싱용 open redirect로 악용될 수 있습니다.
    
- Q. Snowflake ID가 시간순이면 다음 링크를 추측할 수 있지 않나요?
    
    가능합니다. 다만 현재 링크는 SNS에 공개하는 카드와 기록을 가리키고, 링크를 안다고 비공개 데이터에 접근할 수 있는 구조는 아닙니다. 그래서 가역 순열을 기본 발급 경로에 넣기보다 Edge/WAF에서 연속 키 조회를 감시하고 비정상적인 IP·ASN을 제한합니다.
    
    유효 링크 대량 수집이 실제 문제로 확인되면 keyed permutation으로 열거 비용을 높일 수 있습니다. 이 방식도 인증을 대신하지는 않습니다. 비공개 공유 링크라면 Snowflake를 난독화하지 않고, 처음부터 96~128비트 랜덤 토큰과 권한 검사를 사용합니다.
    
- Q. Cassandra가 내려가면 캐시에 없는 링크는 어떻게 되나요?
    
    캐시에 남은 링크는 불변 매핑이므로 `stale-if-error`로 계속 응답할 수 있습니다. 한 번도 캐시되지 않았거나 모든 계층에서 제거된 링크는 Cassandra가 복구될 때까지 조회할 수 없습니다. 모든 링크를 Edge에 영구 보관하는 비용보다 이 실패 범위를 받아들이고, 원본 복구 시간과 인기 링크 캐시 유지율을 SLO로 관리합니다.
    
- Q. RF=3이면 백업도 필요 없지 않나요?
    
    필요합니다. 복제는 노드 장애에는 대응하지만 잘못된 쓰기나 삭제도 세 복제본에 전달합니다. 생성 성공한 매핑은 RF=3과 `LOCAL_QUORUM`으로 단일 노드 장애를 견디고, 오삭제와 운영 실수에는 스냅샷, 리전 밖 백업, 정기 repair로 대응합니다.
