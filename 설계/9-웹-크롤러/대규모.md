# 웹 크롤러
대상: 야구 콘텐츠 수집 서비스

질문: 야구보구의 경기·팀별 피드를 채우려면 외부 뉴스와 블로그, 커뮤니티 글을 계속 발견해야 한다.
경기 종료 직후 새 글을 빠르게 가져오면서도 소수 언론사에 요청을 몰아 보내지 않으려면 수집 경로를 어떻게 설계할 것인가?

> **설계 원칙:** 새 글 발견은 RSS·Atom·제휴 API를 먼저 사용한다. sitemap과 링크 추종 크롤은 빠진 글을 찾는 보완 수단으로 둔다.
> 

관련 장: 4장 처리율 제한 장치, 5장 안정 해시, 6장 키-값 저장소 설계, 7장 유일 ID 생성기 설계

---

## 1. 문제 정의 & 설계 범위 확정

- 서비스: **야구보구 콘텐츠 수집 파이프라인**
    - 승인된 소스에서 새 글을 발견하고, 본문을 파싱해 경기·팀 피드와 검색 인덱스에 전달한다.
- 사용자
    - 직접 사용하는 사람은 없다.
    - 앱 사용자는 정리된 피드를 보고, 운영자는 소스별 수집 상태와 정책을 관리한다.
- 핵심 기능
    - 소스별 수집 방식과 이용 정책 관리
    - 제휴 API, RSS·Atom, sitemap 순으로 새 URL 발견
    - feed가 없거나 누락이 잦은 소스만 제한적으로 링크 추종
    - HTML 다운로드와 본문·메타데이터 파싱
    - URL 중복, 정확 콘텐츠 중복, 유사 기사 중복 제거
- 제외할 범위
    - 피드 랭킹과 개인화 추천
    - 기사 자동 요약과 검색 인덱스 내부 구현
    - 로그인이 필요한 비공개 페이지
    - 이미지·영상 원본 수집
    - JavaScript 렌더링이 필요한 사이트
    - 앱 화면과 출처 표시 UI
- 제약사항
    - 야구 콘텐츠 소스는 수백 host 안팎으로 제한된다고 가정한다. 범용 웹 크롤러처럼 수천 host를 항상 병렬로 돌릴 수 없다.
    - 경기 종료 직후 요청이 소수 주요 언론사에 몰린다. 우선순위를 올려도 host별 요청 상한은 넘을 수 없다.
    - robots.txt뿐 아니라 사이트 이용약관, 제휴 계약, 보관 기간과 노출 범위를 소스별로 지켜야 한다.
    - 전재 기사와 일부 문장만 바꾼 재게시가 많다. 정확 해시만으로는 피드 중복을 충분히 줄이기 어렵다.
    - 외부 사이트는 느려지거나 429를 반환할 수 있다. 한 소스의 장애가 전체 수집을 막으면 안 된다.

### **품질 우선순위**

- 1순위: `robustness + politeness`. 특정 사이트에 요청이 몰리지 않도록 제한하면서, 일부 사이트에 장애가 발생해도 전체 크롤러는 계속 동작해야 한다.
- 2순위: `freshness`. 경기 종료 직후 올라오는 새 글을 가능한 짧은 시간 안에 수집한다.
- 3순위: `coverage / throughput`. 위 조건을 지키면서 수집 범위와 처리량을 늘린다.
- 허용 가능한 희생
    - 실시간성: 수집은 **분 단위 지연**을 허용한다. 초 단위 실시간 수집까지는 목표로 하지 않는다.
    - 완전한 coverage: 모든 웹페이지를 수집하기보다 야구 관련 주요 소스를 allowlist로 관리한다. 저품질·스팸 소스는 제외할 수 있다.
    - 일부 중복·누락: 같은 기사를 중복 수집하거나 일부 글을 놓치는 것은 허용한다.
    - 근사 중복(near-dup): 초기에는 정확히 동일한 콘텐츠를 우선 제거하고, 유사 콘텐츠 판별은 이후에 고려한다.

### **내구성 정의 (SLO)**

- **파싱과 저장까지 완료된 문서는 단일 노드 장애로 유실되지 않아야 한다.**
- 파싱한 문서와 메타데이터는 Cassandra에 RF=3, LOCAL_QUORUM으로 저장한다. raw HTML은 object storage에 별도로 보관한다.
- Frontier의 queue 상태, lease, host별 next-allowed 시각은 영속 저장소에 기록한다. 재시작 시에는 체크포인트를 이용해 전체 상태를 처음부터 다시 계산하지 않도록 한다.
- replication만으로는 잘못 저장된 데이터까지 복구할 수 없다. 파싱 오류가 발생한 경우 다시 처리할 수 있도록 `raw HTML`을 별도로 보관한다.

### **규모**

- 코퍼스(시스템 관리 문서)
    - 대규모 환경을 가정해 약 `2억` 개의 문서를 지속적인 재크롤 대상으로 관리한다. (설계를 위한 가정값)
- 다운로드 처리량(신규 + 재크롤)
    - 목표 월 `10억 fetch`
    - 평균 처리량 = 1,000,000,000 / (30 × 86,400) ≈ `386 fetch/s`
    - 경기 종료 직후 재크롤이 집중되는 시간에는 약 `1,200 ~ 2,000 fetch/s`까지 증가한다고 가정한다.
    - 신규 도메인 유입이나 장애 복구 후 재크롤이 몰리는 상황을 고려해 최대 `5,000 fetch/s`를 처리할 수 있도록 설계한다. (stress target)
- politeness에 따른 처리량 제한
    - host당 초당 1건으로 제한한다면 전체 처리량은 동시에 크롤링할 수 있는 host 수에 영향을 받는다.
        - 최대 전체 처리량 ≈ 활성 host 수 × host당 허용 요청 수
        - 예를 들어 `2,000 fetch/s`를 처리하려면 최소 2,000개의 서로 다른 host에서 동시에 요청을 처리할 수 있어야 한다.
    - 실제 allowlist의 host 수가 이보다 적다면 worker를 추가하는 것만으로 처리량을 높일 수 없다. 이런 경우 RSS·sitemap·공식 API를 우선 활용하거나, 별도로 허용받은 partner host에 대해서만 더 높은 동시성을 적용한다.
- 저장 용량
    - raw HTML의 평균 크기를 500KB, 중복 제거 후 신규 저장량을 월 `2억` 건으로 가정하면 약 `100TB/월`이 필요하다. raw HTML은 object storage에 저장한다.
        - Object Storage는 **대용량 파일을 싸고 내구성 있게 보관하는 용도**
    - 파싱된 본문은 문서당 평균 15KB로 가정한다. `2억 × 15KB ≈ 3TB/월`이며, Cassandra RF=3을 적용하면 약 `9TB/월`이다.
    - 실제 운영에서는 index, compaction 등의 추가 공간까지 고려해야 하므로 장기적으로는 연 수백 TB 규모까지 고려한다.
- 확인 질문
    - 가장 중요한 흐름은?
        - 경기 종료 직후 관련 소스를 재크롤해 피드를 빠르게 최신화하는 것이다.
    - 실시간 처리가 필요한가?
        - 아니다. 분 단위 지연은 허용하지만 host별 요청 제한은 항상 지킨다.
    - 데이터 손실이나 중복을 허용하는가?
        - 저장에 성공한 문서는 유실되지 않아야 한다. 크롤링 과정에서 발생하는 일부 누락이나 중복은 허용한다.
    - 어디까지 수집하나?
        - 야구 관련 allowlist 도메인을 우선 수집한다. 발견한 링크를 따라 외부 도메인으로 계속 확장하지 않는다.
    - 기존 인프라를 활용하는가?
        - 5장의 안정 해시는 host 분산, 6장의 Cassandra·MQ는 저장과 비동기 처리, 7장의 Snowflake는 문서 ID 생성, 4장의 처리율 제한은 크롤링 속도 제어에 활용한다.

## **2. 개략 설계안 제시 & 동의 구하기**

일반적인 웹 크롤러처럼 seed URL에서 시작해 모든 링크를 따라가지는 않는다. 야구 콘텐츠는 수집할 소스가 어느 정도 정해져 있고 경기 종료 직후의 신선도가 중요하기 때문에, 새로운 글을 효율적으로 찾을 수 있는 API와 RSS·Atom feed를 우선 사용한다.

<img width="2048" height="1159" alt="image" src="https://github.com/user-attachments/assets/7f3e57c3-8750-40cc-9f1d-1f879367e83f" />

메달리온 아키텍처(etl , elt) : `Bronze`(원본 데이터) → `Silver`(null 값 제거, 정규화) → `Gold` (실서비스 사용 데이터)

### **수집 경로**

1. `Source Registry`에서 사이트별로 **어떤 방식으로 새 글을 찾을지, 어떤 범위까지 수집할지** 관리한다.
2. 평소에는 `제휴 API`와 `RSS·Atom`을 일정한 간격으로 확인해 새 글을 찾는다. 경기 종료 직후에는 관련 기사가 많이 올라올 수 있으므로 일정 시간 동안 확인 간격을 짧게 한다.
3. `sitemap`도 주기적으로 확인해 API나 RSS·Atom에서 놓친 기사 URL을 보완한다. sitemap이 변경 시각을 제공하는 경우에는 기존 페이지를 언제 다시 확인할지 결정하는 데 참고한다.
4. API나 RSS·Atom을 제공하지 않거나 새 글 누락이 자주 발생하는 승인된 사이트는 정해진 범위 안에서만 페이지의 링크를 따라가며 새로운 기사 URL을 찾는다.
5. 발견한 URL은 불필요한 query parameter 등을 제거해 같은 페이지의 URL을 같은 형태로 만든다. 이후 `URL Seen`에서 이미 발견한 URL인지 확인해 같은 페이지를 반복해서 수집하지 않도록 한다.
6. 처음 발견한 URL은 앞으로 수집할 작업을 관리하는 `URL Frontier`에 넣는다. 여기서 경기 직후 기사와 같은 중요한 작업을 먼저 처리하고, 동시에 사이트별 요청 간격을 지켜 언제 요청할지 결정한다.
7. 요청할 차례가 된 URL은 `Downloader`가 실제 사이트에 요청해 HTML을 가져온다. `Parser`는 가져온 HTML에서 제목, 본문, 게시 시각, 원문 URL 등 필요한 정보를 추출한다.
8. 먼저 본문의 해시를 비교해 내용이 완전히 같은 기사가 있는지 확인한다. 완전히 같지는 않더라도 내용이 비슷한 기사가 있는지 `SimHash`를 이용해 추가로 확인하고, 같은 기사로 판단되면 하나의 중복 그룹으로 묶는다.
9. 마지막으로 `Source Policy`를 확인해 해당 사이트에서 저장이 허용된 데이터만 저장한다. 같은 내용의 기사가 여러 사이트에서 발견됐다면 피드에는 대표 기사 하나를 사용할 수 있도록 묶되, 각 기사의 출처와 원문 URL은 함께 관리한다.

### **API (내부)**

```
소스 정책 조회
SourcePolicy.get()
        ↓
RSS/API에서 새 URL 발견
Discovery.poll()
        ↓
이미 본 URL인지 확인
Seen.register_if_absent()
        ↓ NEW
크롤링 대기열에 등록
Frontier.enqueue()
        ↓
요청 가능한 URL 가져오기
Frontier.lease_ready()
        ↓
HTML 다운로드
Downloader.fetch()
        ↓
Parser로 본문 추출
        ↓
중복 콘텐츠 확인
Dedup.find_cluster()
        ↓
저장
Storage.persist()
        ↓
처리 완료
Frontier.ack()
```

### **데이터 모델**

```
SourcePolicy
- source_id (PK)
- discovery_method (partner_api/rss/atom/sitemap/link_crawl)
- allowed_paths, allowed_fields
- display_mode (link/snippet/full_text)
- raw_retention_days
- default_delay_ms
- attribution

CrawlState
- url_hash (PK)
- source_id, status
- etag, last_modified
- last_fetched_at, next_recrawl_at
- fail_count

Document
- doc_id (PK)
- canonical_url, source_id
- title, snippet, published_at
- team_ids, game_id
- exact_hash, simhash, duplicate_cluster_id

- bucket_date (partition key)
- next_recrawl_at, url_hash (clustering key)
```

Cassandra는 하나의 테이블에 모든 데이터를 넣기보다 조회 패턴에 맞게 테이블을 나눈다. 소스 정책, URL별 크롤링 상태, 문서 정보, 중복 판정 정보, 재방문 대상 등을 각각 필요한 조회 방식에 맞춰 저장한다.

### **주요 컴포넌트**

- Source Registry / Policy
- Partner API, RSS·Atom, Sitemap Poller
- 제한적 Link Crawler
- URL Frontier / Host Scheduler
- HTML Downloader + DNS/robots 캐시
- Parser / URL Filter
- URL Seen / Exact Content Seen / Near-dup Cluster
- Object Storage / Cassandra
- 경기 종료 이벤트 / Freshness Scheduler
- MQ 기반 수집 통계

### 개략적 추정

```
현재 서비스 가정
활성 host     : 300~500개
월 fetch      : 약 1억 건
평균 처리량   : 약 39 fetch/s
peak          : 약 100~200 fetch/s
stress target : host별 요청 제한을 지키면서 최대 300 fetch/s
```

경기 종료 후 30분 동안 feed를 30~~~60초 간격으로 확인한다고 가정해도, 300개 host 기준 feed polling 자체는 초당 약 5\~~~10건이다. 따라서 실제 peak 처리량은 feed polling보다 새로 발견한 기사 HTML을 가져오는 과정에서 발생할 가능성이 높다.

- Go deeper
    - 가장 중요한 요청 흐름: 경기 종료 이벤트 → feed polling → 신규 URL 발견 → 기사 fetch → 중복 판정 → 피드 반영
    - 먼저 생길 수 있는 병목: 주요 host의 요청 제한, Parser CPU 사용량, SimHash 후보 조회
    - 단일 장애 지점: Source Registry, Frontier 상태 및 lease 저장소
    - 처리량 확장: host 또는 source 단위로 작업을 분산하고, Downloader·Parser·Dedup Worker를 독립적으로 수평 확장
    - 주요 실패 상황: feed 누락, `429 Too Many Requests`, 잘못된 near-dup 병합, source policy를 벗어난 데이터 저장

## 3. 핵심 설계 결정 (Decision Log)

<img width="900" height="300" alt="image" src="https://github.com/user-attachments/assets/f52ebd70-d165-4f33-9e75-503cb5a848dc" />

- Decision #1: **새 글은 제휴 API → RSS·Atom → sitemap → 링크 추종 순서로 찾는다**
        
    - 각 방식
        - **`RSS·Atom`**: 사이트가 제공하는 최신 글 feed를 주기적으로 확인해 새 글의 제목과 URL 등을 가져온다.
        - **`sitemap`**: 사이트가 검색 엔진 등을 위해 공개한 URL 목록을 확인할 수 있다.
        - **`링크 추종`**: 직접 웹페이지를 방문해 `<a href>` 같은 링크를 추출하고, 그 링크를 따라가며 새로운 페이지를 찾는다.
    - **해결하려는 문제**
        - 야구보구는 수집할 사이트가 어느 정도 정해져 있다. 새 글을 찾기 위해 매번 사이트의 여러 페이지와 링크를 따라가면 불필요한 요청이 많아지고, 경기 종료 직후 올라오는 새 글을 빠르게 찾기도 어렵다.
    - **선택 이유**
        - 제휴 API와 RSS·Atom은 사이트에서 새로 올라온 글의 목록을 제공하기 때문에 적은 요청으로 새로운 글을 찾을 수 있다.
        - RSS·Atom을 통해 새 글을 우선 확인하고, 여기서 발견하지 못한 글은 사이트의 URL 목록을 제공하는 sitemap으로 보완한다.
        - API, RSS·Atom, sitemap만으로 충분하지 않은 사이트에 대해서만 페이지의 링크를 직접 따라가며 새로운 글을 찾는다.
    - **대안**
        - **링크 추종형 크롤러만 사용**: 사이트의 페이지에서 발견한 링크를 계속 따라가며 새로운 글을 찾는 방식이다. 모든 사이트에 같은 방식을 적용할 수 있지만, 새 글을 찾기 위해 메뉴·카테고리 등 필요하지 않은 페이지까지 방문하게 된다.
    - **트레이드오프**
        - 사이트마다 제공하는 API나 RSS·Atom의 형식이 다르기 때문에 각 형식을 야구보구에서 사용하는 형태로 변환하는 로직이 필요하다.
        - RSS·Atom에는 제목과 URL만 있고 기사 본문이 없는 경우가 있기 때문에, 새 글을 발견한 뒤 실제 기사 페이지를 한 번 더 요청해야 할 수 있다.
    - **재검토 조건**
        - 특정 사이트에서 RSS·Atom으로 새 글을 자주 놓치고 sitemap으로도 충분히 보완되지 않는다면, 해당 사이트에 한해 링크를 직접 따라가는 방식을 추가한다.

- Decision #2: **`URL Frontier`에서 작업 우선순위와 host별 요청 시간을 따로 관리한다**
        
    - **해결하려는 문제**
        - 경기 종료 직후에는 새로운 글을 빨리 찾기 위해 RSS·API를 자주 확인해야 한다.
        - 하지만 같은 사이트에서 다운로드할 기사가 많이 쌓이면 기사 요청을 처리하느라 다음 RSS·API 확인이 늦어질 수 있다.
        - 반대로 RSS·API 확인이 중요하더라도 같은 사이트에 너무 자주 요청해서는 안 된다.
    - **선택 이유**
        - **우선순위 queue**에서는 **어떤 작업을 먼저 처리할지** 결정한다. RSS·API 확인을 가장 먼저 처리하고, 새 기사 다운로드, 기존 문서 재방문 순으로 우선순위를 둔다.
        - **Host Scheduler**에서는 **해당 사이트에 언제 다시 요청할 수 있는지** 관리한다. `next_allowed_at`을 저장해 host별 요청 간격을 지킨다.
        - 따라서 RSS·API 확인처럼 우선순위가 높은 작업도 해당 host의 요청 가능 시간이 되어야 실제 요청을 보낸다.
        - 작업은 `queued → leased → persisted → acked` 상태로 관리한다. Worker가 작업을 가져간 뒤 중간에 장애가 발생해도 다시 처리할 수 있도록 작업 상태를 저장한다.
            - url : naver.com (url frontier: 한 도메인에 한 worker만 처리)
                - a worker : a 작업 수행 (token leased + version = 11) → heartbeat → 네트워크 문제 → X → 업데이트 짠!
                - b worker : a 작업 (token leased  + version=12, `fencing`)
    - **대안**
        - **단일 FIFO**: 들어온 순서대로 작업을 처리하는 방식이다. 기사 다운로드 작업이 많이 쌓이면 그 뒤에 들어온 RSS·API 확인도 함께 늦어져 새로운 글을 발견하는 시간이 길어질 수 있다.
    - **트레이드오프**
        - 작업의 우선순위와 host별 요청 가능 시간을 따로 관리해야 하므로 단일 queue보다 구조가 복잡해진다.
        - RSS·API처럼 높은 우선순위의 작업이 계속 들어오면 기존 문서 재방문 같은 낮은 우선순위 작업이 계속 밀릴 수 있다. 이를 막기 위해 낮은 우선순위 작업에도 일정한 처리 기회를 준다. ( `weighted fair scheduling`)
    - **재검토 조건**
        - RSS·API를 통한 새 글 발견은 빠르지만 기사 다운로드나 기존 문서 재방문이 계속 밀린다면 작업별 우선순위와 처리 비율을 조정한다.

- Decision #3: **사이트별 규칙과 서버 응답에 따라 요청 속도를 조절한다**
        
    - **해결하려는 문제**
        - 경기 종료 직후에는 특정 언론사에 새로운 기사가 많이 올라올 수 있다.
        - 새 글을 빨리 가져오려고 짧은 시간에 많은 요청을 보내면 상대 서버에서 `429 Too Many Requests`를 보내거나 크롤러를 차단할 수 있다.
    - **선택 이유**
        - **Source Policy**에 사이트별 기본 요청 간격을 저장한다. 예를 들어 A 사이트는 1초에 한 번, B 사이트는 2초에 한 번처럼 요청 속도를 다르게 설정할 수 있다.
        - `robots.txt`를 확인해 **크롤링이 허용된 경로인지 확인**하고, 사이트에서 별도의 요청 간격을 안내한다면 이를 반영한다.
        - 서버가 `429 Too Many Requests`를 반환하면 요청이 너무 많다는 의미이므로 속도를 낮춘다. `Retry-After`가 함께 오면 안내된 시간만큼 기다린 뒤 다시 요청한다.
        - 경기 종료 직후에는 새 글을 빨리 찾기 위해 RSS·API를 평소보다 자주 확인하되, 사이트별 요청 제한은 그대로 지킨다.
        - 이전에 확인한 **페이지를 다시 방문**할 때는 `ETag(버**전 식별값)**`와 `Last-Modified`를 사용한다. 내용이 변경되지 않았다면 전체 HTML을 다시 받지 않아도 되므로 불필요한 데이터 전송을 줄일 수 있다.
    - **대안**
        - **작업의 우선순위만 높이기**: RSS·API 확인을 다른 작업보다 먼저 처리할 수는 있지만, 해당 사이트에 더 많은 요청을 보내도 된다는 의미는 아니다. 따라서 요청 속도 제한은 별도로 관리해야 한다.
    - **트레이드오프**
        - 사이트에 요청을 보내는 간격을 길게 잡을수록 서버에 주는 부담은 줄어들지만 새로운 글을 발견하는 시간은 늦어질 수 있다.
        - **특정 사이트의 콘텐츠를 더 빠르게 수집해야 한다면 요청 제한을 임의로 높이기보다 사이트 운영자와 더 높은 요청량을 협의**한다.
    - **재검토 조건**
        - 사이트별로 기사가 게시된 시점부터 야구보구 피드에 반영되기까지 걸리는 시간과 `429` 발생 횟수를 함께 확인한다. 새 글 반영이 너무 느리거나 `429`가 자주 발생한다면 해당 사이트의 요청 주기를 조정한다.

- Decision #4: **URL 중복은 `Bloom Filter`로 빠르게 확인하고, `정확한 저장소`에서 최종 확인한다**
        
    - **해결하려는 문제**
        - 같은 기사 URL이 RSS·Atom, sitemap, 링크 추종 등 여러 경로에서 반복해서 발견될 수 있다.
        - 이를 그대로 처리하면 같은 페이지를 여러 번 다운로드하게 되므로, 새로운 URL인지 이미 본 URL인지 확인해야 한다.
    - **선택 이유**
        - 먼저 URL에서 불필요한 query parameter 등을 제거해 같은 페이지는 같은 URL로 판단할 수 있도록 **정규화**한다.
        - **Bloom Filter**를 이용해 해당 URL을 이전에 본 적이 있는지 빠르게 확인한다.
            - `Bloom Filter`: 여러 해시 함수를 이용해서 비트 배열의 몇 군데를 `1`로 바꾼다.
            - Bloom Filter가 **없다고 판단하면 처음 보는 URL**로 처리한다.
            - Bloom Filter가 **있다고 판단하면 실제로 저장된 URL인지 정확한 저장소에서 한 번 더 확인**한다. Bloom Filter는 처음 보는 URL을 이미 본 URL이라고 잘못 판단할 수 있기 때문이다.
        - 처음 발견한 URL은 `putIfAbsent` 방식으로 등록한다. 여러 Worker가 동시에 같은 URL을 발견하더라도 하나의 Worker만 새 URL로 등록하고 처리할 수 있다. (**원자적 처리**)
    - **대안**
        - **Bloom Filter만 사용**: 적은 메모리로 빠르게 중복 여부를 확인할 수 있지만, 처음 보는 URL을 이미 본 것으로 잘못 판단하는 `false positive`가 발생할 수 있다. 이 경우 실제 새 기사를 수집하지 못할 수 있다.
    - **트레이드오프**
        - Bloom Filter와 실제 URL을 저장하는 정확한 저장소를 함께 관리해야 한다.
        - URL이 다르더라도 실제 기사 내용은 같을 수 있다. URL 중복 확인만으로는 이런 경우를 찾을 수 없기 때문에, 이후 콘텐츠 중복 처리 단계에서 기사 내용도 다시 비교한다.
    - **재검토 조건**
        - 정확한 저장소를 확인하는 요청이 많아져 병목이 발생하면 Bloom Filter의 크기와 false positive 비율을 조정해 저장소 조회 횟수를 줄인다.

- Decision #5: **기사 내용이 완전히 같은지 먼저 확인하고, 이후 비슷한 기사까지 찾아 중복을 판별한다**
        
    - **해결하려는 문제**
        - 같은 기사가 여러 언론사에 그대로 올라오거나, 제목·광고·출처 문구 등 일부만 바뀐 채 다시 게시될 수 있다.
        - URL이 다르기 때문에 URL 중복 검사만으로는 이런 기사를 찾을 수 없고, 그대로 피드에 노출하면 비슷한 기사가 반복해서 보일 수 있다.
    - **선택 이유**
        - 먼저 광고나 불필요한 문구를 제거한 기사 본문으로 **`SHA-256` 해시**를 만든다. 해시가 같으면 본문이 동일한 기사로 판단한다.
        - SHA-256이 다르더라도 내용이 조금만 수정된 같은 기사일 수 있기 때문에 **`SimHash`를 이용해 내용이 얼마나 비슷한지** 추가로 확인한다.
        - 모든 기사와 비교하면 비용이 크기 때문에 최근 72시간 내 같은 팀이나 경기를 다룬 기사로 비교 대상을 먼저 줄인다.
        - 이후 `SimHash` 값에서 서로 다른 비트의 개수인 `Hamming distance`를 비교한다. 차이가 충분히 작으면 내용이 유사한 기사로 판단한다.
        - 중복으로 판단한 기사들은 **하나의 그룹(duplicate cluster)으로 묶고 피드에는 대표 기사 하나만 보여준다**. 각 언론사의 출처와 원문 URL은 삭제하지 않고 모두 보관한다. (fallback, 디버그)
    - **대안**
        - **SHA-256만 사용:** 완전히 같은 기사는 빠르고 정확하게 찾을 수 있지만, 광고나 출처 문구처럼 내용이 조금이라도 달라지면 다른 해시가 만들어진다. 따라서 내용이 거의 같은 전재·재게시 기사를 놓칠 수 있다.
    - **트레이드오프**
        - SimHash는 내용의 유사성을 기준으로 판단하기 때문에 실제로는 서로 다른 기사인데 같은 기사로 잘못 묶을 수 있다.
        - 이를 줄이기 위해 최근 72시간, 같은 팀·경기처럼 비교할 기사 범위를 먼저 좁히고, 실제 기사 데이터를 기준으로 어느 정도 비슷해야 중복으로 볼지 **기준을 조정**한다.
    - **재검토 조건**
        - 피드에 비슷한 기사가 반복해서 노출된다면 중복 판정 범위를 넓힌다.
        - 반대로 서로 다른 기사가 하나의 중복 그룹으로 잘못 묶이는 경우가 많다면 비교 대상이나 SimHash의 중복 판정 기준을 더 엄격하게 조정한다.

- Decision #6: `HTML Downloader` = **여러 사이트가 공용 Worker를 사용하고, 변경된 페이지에만 필요한 데이터를 다시 받는다**
        
- **해결하려는 문제**
    - 외부 사이트마다 응답 속도가 다르기 때문에 특정 사이트의 응답이 느리다고 다른 기사 다운로드까지 함께 늦어지면 안 된다.
    - 특히 경기 종료 직후에는 RSS·API에서 새로운 기사 URL이 한꺼번에 발견될 수 있어 많은 다운로드 요청을 효율적으로 처리해야 한다.
- **선택 이유**
    - 사이트마다 전용 Worker를 따로 만들지 않고, 여러 사이트의 다운로드 작업을 함께 처리하는 **공용 Worker Pool**을 사용한다.
    - 여러 Worker가 동시에 요청을 처리하기 때문에 일부 사이트의 응답이 느리더라도 다른 Worker는 기다리지 않고 다른 기사를 계속 다운로드할 수 있다.
    - 같은 사이트를 요청할 때마다 DNS와 `robots.txt`를 다시 확인하지 않도록 이전에 확인한 결과를 일정 시간 캐시한다.
    - 같은 사이트의 여러 기사를 가져올 때는 가능한 경우 기존 HTTP 연결을 재사용해 매번 새로운 연결을 만드는 비용을 줄인다.
    - 이전에 수집한 페이지를 다시 확인할 때는 `ETag`와 `Last-Modified`를 함께 보낸다. 페이지가 변경되지 않았다면 서버가 `304 Not Modified`를 반환하므로 전체 HTML을 다시 다운로드하지 않아도 된다.
- **대안**
    - **사이트마다 전용 Worker를 사용**: 어떤 Worker가 어떤 사이트를 처리하는지 명확해 구조는 단순하다. 하지만 수집하는 사이트가 많아지면 처리할 작업이 없는 사이트의 Worker도 계속 유지해야 하므로 자원이 낭비될 수 있다.
- **트레이드오프**
    - 외부 사이트가 응답하지 않을 때 Worker가 계속 기다리지 않도록 `timeout`을 설정해야 한다.
    - timeout이 너무 짧으면 단순히 응답이 느린 정상 페이지도 수집하지 못할 수 있고, 너무 길면 응답하지 않는 요청이 Worker를 오래 차지할 수 있다.
    - 따라서 사이트별 실제 응답 시간과 성공률을 확인하면서 적절한 timeout을 조정한다.
- **재검토 조건**
    - 현재 Downloader는 서버에서 받은 HTML을 바로 처리할 수 있는 사이트를 대상으로 한다.
    - JavaScript를 실행해야 기사 본문을 확인할 수 있는 사이트가 많아지면, 일반 다운로드보다 많은 자원을 사용하는 `headless browser`를 별도의 Worker Pool로 분리해 운영한다.

- Decision #7: 저장 = **Source Policy에서 허용한 데이터만 장기 보관한다**    
    
    - **해결하려는 문제**
        - 크롤링한 기사에는 제목, 본문, 출처, 원문 HTML 등 여러 데이터가 포함된다.
        - 기술적으로는 모두 저장할 수 있지만 외부 콘텐츠이기 때문에 사이트별 정책과 계약에 따라 저장하거나 사용자에게 보여줄 수 있는 범위가 다를 수 있다.
        - 또한 `원본 HTML`까지 계속 보관하면 저장 비용도 커진다.
    - **선택 이유**
        - **`Source Policy`**에 사이트별로 **어떤 데이터를 저장할 수 있는지, 사용자에게 어디까지 보여줄 수 있는지, 원본을 얼마나 오래 보관할지**를 설정한다.
        - 기본적으로 피드에는 기사 전문을 그대로 보여주지 않고 제목, 짧은 내용 요약(snippet), 출처와 원문 링크만 보여준다.
        - 다운로드한 **`원본 HTML`은 Parser에 문제가 생겼을 때 다시 파싱할 수 있도록 Object Storage에 임시로 보관**한다. 기본 보관 기간은 30일로 두고 이후 삭제한다.
        - 서비스에서 계속 사용하는 제목, 원문 URL, 작성일, 팀·경기 정보와 같은 문서 데이터는 Source Policy에서 허용한 범위 내에서 `Cassandra`에 저장한다.
        - 중복으로 판단한 기사들의 관계도 `Cassandra`에 저장해 어떤 기사들이 같은 기사 그룹으로 묶였는지 관리한다.
            - 대량 데이터를 여러 노드에 나눠 저장하면서 쓰기 처리량을 수평 확장 가능
            - mysql에 저장해도 된다.
    - **대안**
        - **기사 본문과 원본 HTML을 모두 계속 보관**: Parser가 변경되더라도 과거 문서를 언제든 다시 처리할 수 있다는 장점이 있다. 하지만 데이터가 계속 쌓여 `저장 비용`이 커지고, 사이트별 콘텐츠 저장 정책이나 계약 조건을 지키기도 어려워진다.
    - **트레이드오프**
        - 원본 HTML을 짧게 보관할수록 저장 비용은 줄어든다.
        - 반면 보관 기간이 지난 기사는 원본 HTML이 남아 있지 않기 때문에 Parser를 개선하더라도 과거 기사를 다시 파싱하기 어렵다.
    - **재검토 조건**
        - 기사 본문 사용이나 원본의 장기 보관이 별도로 허용된 사이트가 생기면 해당 Source Policy에 맞게 저장 범위와 보관 기간을 늘린다.

- Decision #8: Freshness = **경기 종료 직후에는 일정 시간 동안 새 글을 더 자주 확인한다**
        
    - **해결하려는 문제**
        - 평소에는 새로운 야구 기사가 자주 올라오지 않기 때문에 `RSS·API`를 너무 자주 확인하면 불필요한 요청이 많아진다.
        - 반면 경기 종료 직후에는 관련 기사가 짧은 시간에 많이 올라오기 때문에 평소와 같은 간격으로 확인하면 새 기사를 늦게 발견할 수 있다.
    - **선택 이유**
        - 평소에는 사이트별 기사 등록 빈도에 따라 `RSS·API`를 약 5~15분 간격으로 확인한다.
        - 경기 종료 직후에는 관련 기사가 많이 올라올 가능성이 높으므로, 관련 사이트의 RSS·API를 예를 들어 30~60초 간격으로 30분 동안 확인한다. (더 자주 확인)
        - 30분이 지나면 다시 평소의 확인 주기로 돌아가 불필요한 요청을 줄인다.
        - 경기 직후 다운로드해야 할 기사가 많이 쌓이더라도 새로운 기사를 계속 발견할 수 있도록 **RSS·API 확인 작업에는 높은 우선순위**를 준다.
        - 단, 확인 주기를 짧게 하더라도 각 사이트에 설정한 요청 속도 제한은 그대로 지킨다.
    - **대안**
        - **경기 종료 직후 관련 사이트 전체를 자주 다시 크롤링**: 새 기사가 올라왔는지 확인할 수는 있지만 변경되지 않은 페이지까지 반복해서 요청하게 된다. 따라서 사이트 전체를 다시 확인하기보다 새 글 목록을 제공하는 RSS·API를 집중적으로 확인하는 것이 효율적이다.
    - **트레이드오프**
        - 경기 종료 후 확인 주기를 짧게 하면 새로운 기사를 더 빨리 발견할 수 있지만 그만큼 외부 사이트에 보내는 요청도 증가한다.
        - 또한 실제로 관련 기사가 올라오지 않는 사이트까지 자주 확인하면 불필요한 요청이 생길 수 있으므로 **어떤 경기와 어떤 사이트가 관련 있는지 적절히 관리**해야 한다.
    - **재검토 조건**
        - 실제 운영 데이터를 보고 확인 주기를 조정한다.
        - 기사가 게시된 뒤 야구보구 피드에 반영되기까지 너무 오래 걸린다면 RSS·API를 더 자주 확인한다.
        - 반대로 확인할 때마다 변경된 내용이 없는 경우가 지나치게 많다면 너무 자주 확인하고 있다는 의미이므로 확인 간격을 늘린다.

- Decision #9: 분산 = **안정 해시로 host별 담당 노드를 정하고, 장애가 발생해도 하나의 노드만 처리하도록 한다**
        
    - **해결하려는 문제**
        - 크롤러 서버가 여러 대라면 수집할 사이트(host)를 각 서버에 나누어 처리해야 한다.
        - 이때 **같은 host를 여러 서버가 동시에 크롤링**하면 각 서버는 요청 간격을 지키더라도 실제 사이트에는 더 많은 요청이 전달되어 host별 요청 제한을 초과할 수 있다.
        - 특히 담당 서버에 장애나 네트워크 문제가 발생해 다른 서버가 작업을 넘겨받는 과정에서 기존 서버와 새로운 서버가 동시에 같은 host를 처리할 수 있다.
    - **선택 이유**
        - **안정 해시**를 사용해 각 host를 기본적으로 어떤 노드가 담당할지 정한다. 노드가 추가되거나 제거되어도 일부 host만 새로운 노드로 이동하기 때문에 작업을 다시 배분하는 범위를 줄일 수 있다.
        - 다만 안정 해시는 기본 담당자를 정할 뿐이므로, 실제 크롤링을 시작하기 전에는 **일정 시간 동안 유효한 처리 권한인 `lease`**를 획득하도록 한다.
        - 정상적으로 동작하는 노드는 lease를 계속 갱신한다. 노드에 장애가 발생해 갱신하지 못하면 lease가 만료되고 다른 노드가 해당 host의 처리 권한을 가져갈 수 있다.
        - 담당 노드가 바뀔 때마다 `epoch` 번호를 증가시킨다. 이전 담당 노드가 뒤늦게 복구되어 작업 결과를 저장하려고 해도 오래된 epoch라면 요청을 거부한다. (**`fencing`**)
            - 이를 통해 장애가 발생해 담당 노드가 변경되더라도 이전 노드와 새로운 노드가 동시에 같은 host의 상태를 변경하는 것을 막는다.
    - **대안**
        - **안정 해시만 사용**: 평상시에는 host를 여러 노드에 안정적으로 나눌 수 있다. 하지만 네트워크 문제로 기존 노드가 완전히 죽지 않은 상태에서 다른 노드가 작업을 넘겨받으면 두 노드가 모두 자신이 담당자라고 판단할 수 있다.
    - **트레이드오프**
        - 현재 어떤 노드가 host를 처리할 권한을 가지고 있는지 저장하는 lease 저장소가 추가로 필요하다.
        - 노드는 자신의 lease가 만료되지 않도록 주기적으로 갱신해야 하며, 작업 결과를 저장할 때도 현재 담당 노드의 epoch가 맞는지 확인해야 하므로 구현이 복잡해진다.
    - **재검토 조건**
        - 정상적으로 동작하는 노드의 lease가 자주 만료되어 담당 노드가 불필요하게 바뀌거나, 이전 epoch의 요청이 자주 거부된다면 lease의 유효 시간과 장애를 판단하는 시간을 함께 조정한다.

- Decision #10: 방어 = **승인된 사이트만 수집하고, 비정상적인 URL이나 응답은 차단한다**
        
    - **해결하려는 문제**
        - 웹페이지에서 발견한 링크를 모두 따라가면 URL만 조금씩 바뀌면서 무한히 생성되는 페이지를 계속 수집할 수 있다.
        - 기사 HTML 대신 지나치게 큰 파일이나 필요하지 않은 이미지·영상 등이 반환되면 크롤러의 자원을 불필요하게 사용할 수 있다.
        - 또한 크롤러 서버가 외부에서 발견한 URL에 직접 요청을 보내기 때문에, 악의적으로 만들어진 URL을 통해 회사 내부 서버에 접근하지 못하도록 막아야 한다.
    - **선택 이유**
        - 야구보구는 인터넷 전체를 수집할 필요가 없으므로 기본적으로 미리 승인한 도메인과 경로만 크롤링한다.
        - 새로운 도메인의 링크를 발견하더라도 바로 따라가지 않고 별도의 검토 대상으로 등록하고, 승인된 이후에만 수집한다.
        - 요청할 URL이 지나치게 길거나 경로가 너무 깊고 query parameter가 과도하게 많은 경우에는 비정상적인 URL일 가능성이 있으므로 수집하지 않는다.
        - URL의 실제 IP 주소와 redirect 이후의 주소를 확인해 회사 내부망이나 사설 IP로 연결되는 요청은 차단한다.
        - HTML 대신 지나치게 큰 데이터가 전달되어 크롤러의 자원을 과도하게 사용하지 않도록 다운로드 크기와 압축 해제 후 크기를 제한한다.
        - 기사 수집에 필요한 HTML 등 허용된 데이터만 받을 수 있도록 응답의 **`MIME type`**도 확인한다.
    - **대안**
        - **발견한 링크를 모두 따라가며 수집**: 더 많은 페이지를 발견할 수 있다는 장점이 있다. 하지만 URL이 무한히 생성되는 페이지에 빠지거나, 크롤러를 이용해 내부 서버에 요청을 보내는 등의 문제를 막기 어려워진다.
    - **트레이드오프**
        - 제한을 너무 강하게 설정하면 정상적인 기사도 비정상적인 요청으로 판단해 수집하지 못할 수 있다.
        - 따라서 요청이 차단되면 URL 길이 초과, 응답 크기 초과, 허용되지 않은 주소 등 차단된 이유를 함께 기록한다.
    - **재검토 조건**
        - 승인된 사이트의 정상적인 기사가 같은 제한에 반복해서 걸린다면 전체 제한을 완화하기보다 해당 사이트의 특성을 확인한 뒤 Source Policy를 조정한다.

## **4. 상세 설계**

### **경기 종료 뒤 기사 하나를 가져오는 흐름**

1. 경기가 종료되면 해당 경기의 팀과 관련된 수집 대상 사이트(source)를 찾는다.
2. Source Registry에서 각 사이트가 제휴 API, RSS·Atom, sitemap 중 어떤 방식으로 새 글을 제공하는지와 사이트별 요청 간격을 확인한다.
3. 관련 사이트의 제휴 API와 RSS·Atom을 확인하는 작업을 높은 우선순위로 URL Frontier에 등록한다.
4. Host Scheduler는 사이트별 요청 간격을 지키면서 새 글을 확인하는 작업을 처리한다.
5. 새 글 목록이 변경되었다면(`200`) 기사 URL을 가져온다. 이전 확인 이후 변경되지 않았다면(`304`) HTML을 다시 받지 않고 다음 확인 시간만 설정한다.
6. 발견한 URL은 불필요한 query parameter 등을 정리해 같은 주소를 같은 형태로 만든 뒤, 이미 발견한 URL인지 확인한다. 처음 발견한 URL만 원자적으로 등록해 여러 Worker가 같은 기사를 중복으로 처리하지 않도록 한다.
7. 처음 발견한 기사라면 실제 HTML을 가져오기 위한 작업을 article fetch queue에 등록한다.
8. Downloader가 기사 HTML을 가져오고 Parser가 제목, 본문, 게시 시각, 원문 URL 등의 정보를 추출한다.
9. 먼저 본문의 SHA-256 해시를 비교해 완전히 같은 기사가 있는지 확인한다. 완전히 같지는 않다면 최근에 올라온 같은 팀·경기 관련 기사들과 SimHash를 비교해 내용이 비슷한 기사인지 확인한다.
10. 기존 기사와 내용이 비슷하다면 같은 duplicate cluster로 묶고 새로운 출처와 원문 URL을 추가한다. 비슷한 기사가 없다면 새로운 cluster를 만든다.
11. Source Policy를 확인해 저장이 허용된 데이터만 Cassandra에 저장한다. 원본 HTML은 재파싱이 필요한 경우를 위해 정책에서 정한 기간 동안 Object Storage에 보관한다.
12. 저장까지 성공하면 Frontier에 작업 완료(ACK)를 기록하고, 대표 기사를 피드와 검색 파이프라인으로 전달한다.

### **Feed가 없는 source**

제휴 API나 RSS·Atom을 제공하지 않는 사이트는 먼저 sitemap에서 새로운 기사 URL을 찾는다.

sitemap도 제공하지 않거나 새 글 반영이 늦은 경우에는 사전에 승인한 기사 목록 페이지에서만 링크를 찾아 새로운 기사 URL을 발견한다.

이때 링크를 무제한으로 따라가지 않는다. Source Policy에 수집할 수 있는 경로와 링크를 따라갈 수 있는 최대 깊이를 미리 정해두고 그 범위 안에서만 수집한다. 수집 중 새로운 외부 도메인을 발견하더라도 자동으로 이동하지 않고 별도의 검토 대상으로 등록한다.

### **Freshness와 Politeness가 충돌할 때**

경기 종료 직후에는 새로운 기사를 빨리 발견해야 하지만, 그렇다고 특정 사이트에 설정된 요청 속도 제한을 넘을 수는 없다.

따라서 같은 사이트의 RSS·API 확인 작업과 기사 HTML 다운로드 작업을 하나의 FIFO queue에서 순서대로 처리하지 않는다. 기사 다운로드 작업이 많이 쌓이더라도 새 글을 확인하는 RSS·API 요청이 계속 처리될 수 있도록 일정한 처리 기회를 우선 보장한다.

```
한 host가 처리할 수 있는 요청
        ↓
일부 → RSS·API 확인
나머지 → 발견한 기사 HTML 다운로드
```

단, 두 종류의 요청을 합친 전체 요청량은 해당 사이트에 설정된 요청 제한을 넘지 않는다.

운영하면서 기사가 게시된 뒤 야구보구 피드에 반영되기까지 너무 오래 걸리는데 `429 Too Many Requests`가 발생하지 않는다면 RSS·API 확인 간격을 조금 줄일 수 있다.

반대로 이미 `429`가 발생하고 있다면 요청을 더 늘리지 않는다. 더 빠른 수집이 필요하다면 해당 사이트와 더 높은 요청 한도를 협의하거나 불필요한 기사 다운로드를 줄이는 방향으로 해결한다.

### **Near-dup 판정**

새로운 기사 하나를 기존의 모든 문서와 비교하지 않는다. 문서가 수천만 건이라면 기사 하나가 들어올 때마다 전체 문서를 비교하는 것은 비용이 너무 크기 때문이다.

먼저 SHA-256을 이용해 본문이 완전히 같은 기사가 있는지 확인한다. 완전히 같은 기사가 없다면 최근 72시간 안에 게시되었고 같은 팀이나 경기를 다루는 기사처럼 **중복일 가능성이 높은 문서만 후보로 가져온다.**

그 후보들의 SimHash를 비교해 문구나 광고 등 일부 내용만 다른 비슷한 기사인지 확인한다.

```
새 기사
  ↓
SHA-256
  ↓
완전히 같은 기사?
  ├─ YES → 같은 cluster
  │
  └─ NO
      ↓
최근 72시간 + 같은 팀·경기 후보 조회
      ↓
SimHash 비교
      ↓
충분히 비슷함 → 같은 cluster
다름          → 새로운 cluster
```

초기에는 서로 다른 기사를 같은 기사로 잘못 묶지 않는 것을 더 중요하게 본다. 실제 기사 쌍을 사람이 확인한 데이터를 기준으로 SimHash 기준을 정하고, 중복 기사가 피드에 계속 반복해서 노출될 때 조금씩 기준을 조정한다.

같은 cluster로 묶더라도 각 언론사의 출처, 원문 URL과 게시 시각은 모두 보존한다. 이를 통해 피드에서는 대표 기사 하나만 보여주면서도 어떤 사이트에서 같은 내용의 기사가 게시되었는지 관리할 수 있다.

### **저장과 정책 적용**

기사의 파싱과 중복 판정이 끝나면 Source Policy를 확인한 뒤 저장한다.

```
Source Policy 확인
        ↓
어떤 데이터를 저장할 수 있는지 확인
        ↓
허용된 문서 데이터 → Cassandra
        ↓
재파싱용 raw HTML → Object Storage
        ↓
duplicate cluster 갱신
        ↓
Frontier ACK
```

Cassandra에는 제목, 원문 URL, 게시 시각, 팀·경기 정보 등 서비스에서 계속 사용하는 구조화된 데이터를 저장한다. 대규모 문서를 key 기반으로 읽고 쓰는 패턴이며, 기존 서비스에서 운영 중인 Cassandra를 활용한다.

원본 HTML은 서비스에서 직접 사용하기 위한 데이터가 아니라 Parser 오류가 발생했을 때 다시 처리하기 위한 원본이다. 따라서 Object Storage에 Source Policy에서 정한 기간 동안만 보관하고, 기간이 지나면 자동으로 삭제한다.

기본적으로 사용자에게는 기사 전문을 그대로 보여주지 않고 제목, 짧은 snippet, 출처와 원문 링크만 제공한다. 기사 본문 저장이나 노출이 별도로 허용된 source가 있다면 해당 Source Policy에 맞게 저장 범위와 보관 기간을 다르게 적용한다.

## 4. 상세 설계

### 경기 종료 뒤 기사 하나를 가져오는 흐름

1. 경기 종료 이벤트가 팀과 연결된 source 목록을 찾는다.
2. Source Registry에서 각 source의 discovery 방식과 요청 간격을 읽는다.
3. Partner API와 RSS·Atom 요청을 high priority discovery queue에 넣는다.
4. Host Scheduler가 source별 간격 안에서 discovery 요청 몫을 먼저 배정한다.
5. 200 응답이면 새 entry의 GUID와 URL을 읽고, 304면 다음 polling 시각만 갱신한다.
6. URL을 정규화한 뒤 정확 집합에 `putIfAbsent`로 등록한다.
7. 새 URL이면 article fetch queue에 넣는다.
8. Downloader가 HTML을 받고 Parser가 제목, 본문, 게시 시각, canonical URL을 추출한다.
9. SHA-256 exact hash를 확인한 뒤 최근 같은 팀·경기 후보와 SimHash를 비교한다.
10. 기존 cluster와 유사하면 출처를 추가하고, 아니면 새 cluster를 만든다.
11. source policy가 허용한 필드와 raw 보관 기간을 적용해 저장한다.
12. 저장이 끝나면 Frontier를 ACK하고 대표 기사를 피드·검색 파이프라인에 전달한다.

### Feed가 없는 source

먼저 sitemap에서 새 URL을 찾는다. sitemap도 없거나 늦다면 승인된 목록 페이지에서만 링크를 추출한다. 링크 추종 범위는 source policy에 경로와 최대 depth로 고정한다. 외부 도메인은 자동으로 따라가지 않는다.

### Freshness와 politeness가 충돌할 때

같은 host에서 discovery와 article fetch를 단일 FIFO로 섞지 않는다. 요청 상한 안에서 discovery lane에 최소 몫을 남긴다. 기사 backlog가 커져도 다음 RSS polling이 끝없이 밀리지 않게 하기 위해서다.

그래도 host 상한은 넘지 않는다. p95 게시-노출 지연이 목표를 넘고 429가 없다면 polling 간격을 줄인다. 이미 429가 발생한다면 API·feed 제공자와 허용률을 협의하거나 기사 fetch 수를 줄여야 한다.

### Near-dup 판정

전체 2,000만 문서와 SimHash를 비교하지 않는다. 최근 72시간, 같은 팀·경기, 비슷한 게시 시각의 후보만 가져온다. 정확 해시는 같은 문서를 바로 찾고, SimHash는 문장이 조금 바뀐 재게시를 찾는다.

잘못 합치는 비용이 크므로 초기에는 보수적인 임계값을 쓴다. 라벨링한 기사 쌍으로 precision을 먼저 확인하고, 중복이 계속 노출될 때만 recall을 높인다. cluster에는 대표 기사뿐 아니라 모든 출처 URL과 게시 시각을 보존한다.

### 저장과 정책 적용

```text
SourcePolicy 확인
→ raw HTML 저장 여부와 만료 시각 결정
→ 허용된 필드만 Cassandra에 기록
→ duplicate cluster 갱신
→ Frontier ACK
```

기본 모드는 원문 링크와 제목, 짧은 snippet만 노출한다. 전문 저장·노출은 계약이 있는 source만 허용한다. raw 보관 기간이 끝나면 Object Storage lifecycle이 삭제하고 Cassandra의 `raw_object_key` 상태를 갱신한다.

### 장애 시 동작

#### Feed가 늦거나 잘못된 entry를 줄 때

GUID만 믿지 않고 canonical URL과 게시 시각을 함께 확인한다. feed 누락률이 반복해서 높으면 sitemap 또는 제한적 링크 추종을 보완 경로로 켠다.

#### 대상 사이트가 429를 보낼 때

`Retry-After` 뒤로 `next_allowed_at`을 옮긴다. 경기 종료 이벤트가 들어와도 이 시각을 앞당기지 않는다.

#### Downloader가 죽을 때

ACK되지 않은 lease는 만료 뒤 다시 실행한다. URL 등록, object key, 문서 ID와 cluster 갱신은 멱등하게 만든다.

#### Dedup Worker가 밀릴 때

원문 저장은 완료하되 피드 노출을 잠시 보류한다. near-dup 검사를 건너뛰고 중복 기사를 바로 노출하지 않는다. lag가 회복되면 대기 문서를 순서대로 cluster에 넣는다.

#### 정책을 잘못 적용했을 때

source_id로 저장 문서를 찾고 노출을 즉시 중단한다. raw와 본문은 정책에 맞춰 삭제 또는 재처리한다. 정책 변경과 삭제 작업은 감사 로그에 남긴다.

### 확장 방식

현재 규모에서는 source adapter와 정책 운영이 분산 처리보다 먼저 어렵다. host가 수천 개로 늘고 월 fetch가 10억 건에 가까워질 때 Downloader·Parser·Dedup Worker를 늘리고 source_id 또는 host로 partition을 나눈다. 처리량 숫자만 키우기 위해 범용 크롤러 구조를 먼저 운영하지 않는다.

## 5. 운영과 마무리

### 운영에서 먼저 볼 신호

- discovery: source별 feed 성공률, 신규 URL 수, feed 누락률, 304 비율
- freshness: 게시 시각부터 발견·파싱·노출까지의 p50·p95
- politeness: host별 요청 간격, 403·429, Retry-After 준수율
- near-dup: cluster 비율, 중복 노출 신고, 잘못된 병합 신고, 후보 조회 지연
- 정책: 허용 필드 위반, raw 만료 지연, 출처 누락
- Frontier: discovery/article queue 대기, lease 만료, fencing 거부
- 저장: Cassandra·Object Storage 실패, orphan object

### 알람을 받았을 때

게시-발견 지연만 늘면 경기 이벤트와 source 매핑, feed polling 주기부터 본다.

feed는 제때 도는데 게시-노출 지연이 늘면 article fetch, Parser, near-dup queue를 순서대로 확인한다.

429와 discovery 지연이 함께 늘면 polling을 더 당기지 않는다. Retry-After와 source별 요청 예산을 확인한다.

중복 노출이 늘면 SimHash 후보 범위와 임계값을 보고, 잘못된 병합이 늘면 임계값을 보수적으로 되돌린다.

raw 만료 지연이나 허용되지 않은 필드가 발견되면 해당 source의 노출을 먼저 중단한다.

### 트래픽이 10배가 되면

1. source 수와 기사 발행량이 실제로 늘었는지 확인한다.
2. feed/API coverage를 높여 목록 페이지와 링크 추종 요청을 줄인다.
3. discovery lane과 article lane의 비율을 조정한다.
4. Parser와 near-dup 후보 조회를 source·시간 bucket으로 partition한다.
5. 그다음 Downloader, Cassandra, Object Storage를 측정된 병목에 맞춰 늘린다.

### 추가로 검토할 내용

- WebSub처럼 push를 지원하는 source의 polling 제거
- 언론사별 adapter 변경 감지
- 한국어 기사 near-dup 평가 데이터셋
- 삭제 요청과 정책 변경 자동화
- 승인된 SPA source의 격리된 headless browser pool

## 컴포넌트 블록

- Source Registry / Policy
    - 고려할 때: source마다 수집 방식, 계약, robots, 보관 기간이 다름
    - 주의할 때: 정책 변경이 Parser와 Storage에 늦게 반영되는 문제
    - 정책: discovery_method, allowed_fields, display_mode, raw_retention_days, attribution
    - **Go deeper:** Audit Log · Versioning · Takedown · Policy propagation
- RSS·Atom / Sitemap Poller
    - 고려할 때: 적은 요청으로 새 URL 발견
    - 주의할 때: 잘못된 GUID, feed 누락, 오래된 sitemap
    - 정책: 조건부 요청, source별 cursor, 경기 이벤트 기반 polling
    - **Go deeper:** ETag · Last-Modified · Backoff · Adapter
- URL Frontier
    - 고려할 때: discovery와 article fetch 우선순위, host별 요청 시각
    - 주의할 때: discovery starvation, lease 만료, queue 적체
    - 정책: weighted front queue + host scheduler + lease·ACK
    - **Go deeper:** Fair Queue · Backpressure · Retry · Recovery
- Dedup
    - 고려할 때: 같은 URL, 완전한 본문 중복, 일부만 바뀐 재게시
    - 주의할 때: near-dup 오탐과 후보 검색 비용
    - 정책: Bloom + 정확 집합, SHA-256, 최근 후보 SimHash cluster
    - **Go deeper:** Hamming Distance · Candidate Partition · Evaluation Set
- Storage
    - 고려할 때: 메타데이터 장기 보관과 raw 단기 보관 분리
    - 주의할 때: 정책 위반 필드, raw 만료, orphan object
    - 정책: Object Storage lifecycle + Cassandra 조회별 테이블
    - **Go deeper:** RF=3 · LOCAL_QUORUM · Lifecycle · Reconciliation
- Host Ownership
    - 고려할 때: 여러 Downloader 노드에서 host별 politeness 유지
    - 주의할 때: 네트워크 분할과 늦은 ACK
    - 정책: 안정 해시로 기본 배정, lease와 epoch fencing으로 실행 권한 확인
    - **Go deeper:** Lease TTL · Heartbeat · Failover · Virtual Node

- [ ]  host별 요청 상한과 freshness의 충돌을 설명했는가
- [ ]  URL, exact content, near-dup을 다른 단계에서 처리하는가
- [ ]  SimHash 후보 범위와 오탐 비용을 설명했는가
- [ ]  SourcePolicy가 저장·보관·노출 전에 적용되는가

- [ ]  429, Retry-After, redirect, DNS rebinding을 다뤘는가

## 🎤 면접 5분 스크립트

> 설명 순서: 요구사항과 규모 60초 → 수집 경로와 Frontier 90초 → 중복·저장 90초 → freshness·장애 대응 60초
> 
- 1) 문제와 규모 (60초)
    
    설계할 것은 야구보구의 경기·팀별 피드를 채우는 콘텐츠 수집 파이프라인입니다. 중요한 점은 범용 웹 전체가 아니라 승인된 야구 source 수백 개를 다룬다는 것입니다.
    
    현재 규모는 300에서 500 host, 관리 문서 2,000만 건, 월 1억 fetch를 가정했습니다. 평균은 약 39 fetch/s이고 경기 종료 직후 peak는 100에서 200 fetch/s입니다. 수천 host와 월 10억 fetch는 서비스가 실제로 확장됐을 때의 별도 시나리오로 둡니다.
    
- 2) 수집 경로와 Frontier (90초)
    
    새 글 발견은 제휴 API, RSS·Atom, sitemap 순으로 처리합니다. 링크 추종은 feed가 없거나 누락이 반복되는 승인 source에만 씁니다. 이 방식이 범용 BFS 크롤보다 요청 수가 적고 경기 뒤 새 글도 빨리 찾습니다.
    
    Frontier는 discovery, 새 기사, 일반 재방문의 우선순위를 나누고 Host Scheduler가 source별 요청 간격을 지킵니다. 기사 backlog가 쌓여도 RSS polling이 밀리지 않도록 discovery lane에 요청 몫을 남깁니다. 작업은 lease와 ACK로 처리합니다.
    
- 3) 중복과 저장 (90초)
    
    중복은 세 단계입니다. URL은 Bloom filter와 정확 집합의 putIfAbsent로 다운로드 전에 막습니다. 본문이 완전히 같으면 SHA-256으로 처리합니다. 전재 기사처럼 일부만 다르면 최근 같은 팀·경기 후보 안에서 SimHash를 비교해 duplicate cluster로 묶습니다.
    
    피드에는 대표 기사 한 건을 보여주되 원문 출처는 모두 남깁니다.
    
    저장 전에 SourcePolicy를 확인합니다. 기본은 제목, 짧은 snippet, 출처, 원문 링크만 노출하고 raw HTML은 30일만 보관합니다. 전문 저장과 노출은 계약이 있는 source만 허용합니다.
    
- 4) Freshness와 장애 대응 (60초)
    
    경기가 끝나면 관련 feed polling을 예시로 30에서 60초 간격으로 30분간 올렸다가 다시 낮춥니다. ETag와 Last-Modified로 변경되지 않은 응답의 전송량을 줄입니다. host별 상한과 Retry-After는 경기 이벤트가 와도 넘지 않습니다.
    
    노드 장애 뒤에는 새 owner가 더 높은 epoch의 host lease를 얻고, 이전 owner의 ACK는 fencing으로 거부합니다.
    
    운영에서는 게시부터 노출까지의 지연, source별 feed 누락, 429, near-dup 오탐을 함께 봅니다.
    

## ❓ 예상 꼬리질문 Q&A

- Q. 야구 뉴스라면 RSS만 쓰면 되지 않나요?
    
    RSS가 있는 source는 우선 사용합니다. 다만 feed가 없거나 제목과 URL만 제공하거나 일부 글을 누락하는 source가 있습니다. sitemap과 제한적 링크 추종은 이 누락을 보완하는 경로이고, 모든 source에 범용 크롤을 적용하지는 않습니다.
    
- Q. 그러면 대규모 크롤러라고 부르기 어려운 것 아닌가요?
    
    현재 야구보구 기준은 수백 host와 월 1억 fetch입니다. 수천 host와 월 10억 fetch는 범용 콘텐츠 플랫폼으로 확장할 때의 시나리오입니다. 현재는 source adapter, policy, near-dup 품질이 분산 워커 수보다 더 중요한 문제입니다.
    
- Q. 경기 뒤 polling을 당기면 politeness를 어기지 않나요?
    
    host별 요청 상한 안에서 discovery 요청의 순서만 앞당깁니다. 조건부 요청을 사용하고 429·Retry-After가 오면 즉시 늦춥니다. 더 빠른 주기가 필요하면 기술적으로 우회하지 않고 provider와 허용률을 협의합니다.
    
- Q. SimHash가 다른 기사를 하나로 합치면 어떻게 하나요?
    
    최근 72시간과 같은 팀·경기 후보로 비교 범위를 제한합니다. 임계값은 라벨링한 기사 쌍으로 precision을 먼저 맞춥니다. cluster에는 모든 원문을 보존하므로 잘못 합친 경우 분리할 수 있습니다.
    
- Q. 기사 본문을 저장해도 되나요?
    
    모든 source에 같은 답을 적용하지 않습니다. SourcePolicy에 계약, 허용 필드, 노출 방식, raw 보관 기간을 저장합니다. 기본은 제목과 짧은 snippet, 출처, 원문 링크이며 전문 저장·노출은 명시적으로 허용된 source만 사용합니다.
    
- Q. Bloom filter 때문에 새 URL을 놓치지 않나요?
    
    positive일 때 정확 집합을 다시 확인하므로 false positive는 저장소 조회만 늘립니다. 최종 등록은 putIfAbsent로 처리해 RSS와 sitemap에서 동시에 발견한 URL도 한 번만 넣습니다.
    
- Q. 안정 해시가 있는데 lease도 필요한가요?
    
    안정 해시는 기본 담당 노드를 정합니다. 네트워크 분할 중에는 두 노드가 같은 host를 담당한다고 판단할 수 있습니다. host lease와 epoch fencing으로 이전 owner의 상태 갱신을 막습니다.
    
- Q. Dedup Worker가 밀리면 near-dup을 건너뛰나요?
    
    건너뛰고 바로 피드에 노출하면 중복 기사가 쌓입니다. 원문 저장까지만 끝내고 피드 노출을 보류합니다. lag가 회복되면 대기 문서를 cluster에 넣고 대표 기사를 결정합니다.
    
- Q. Feed가 잘못된 URL을 주면 어떻게 하나요?
    
    GUID만 신뢰하지 않고 URL 정규화와 canonical URL, 게시 시각을 함께 확인합니다. 같은 URL은 정확 집합에서 걸러지고, 다른 URL의 같은 기사는 콘텐츠 중복 단계에서 묶입니다.
    
- Q. 트래픽이 10배가 되면 무엇부터 바꾸나요?
    
    먼저 source 수와 기사 발행량이 실제로 늘었는지 확인합니다. feed와 API coverage를 높여 링크 추종 요청을 줄이고, Parser와 near-dup 후보 조회를 source·시간 bucket으로 나눕니다. 그다음 측정된 병목에 맞춰 Downloader와 저장소를 늘립니다.
