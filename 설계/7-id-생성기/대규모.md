# 7. 분산 시스템을 위한 유일 id 생성기 설계 (대규모)

- **대상:** 직관 기록·채팅처럼 append 데이터가 수십억 건까지 쌓이고, 여러 노드에 분산 저장하는 서비스.

- **문제:** 경기 종료 직후 쓰기가 몰리는 상황에서 단일 MySQL의 `AUTO_INCREMENT`에 계속 의존하면 ID 발급 지점이 병목이 된다. 저장소를 분산해도 ID를 한곳에서 발급하면 쓰기 경로에 중앙 의존성이 남게 된다.

- **질문:** 여러 서버가 동시에 ID를 발급하는 환경에서, 중앙 서버와 매번 통신하지 않고 **시간순 정렬이 가능한 64-bit 유일 ID를 어떻게 만들 것인가?**

---

## 1. 문제 정의 & 설계 범위 확정

- 서비스: 야구 직관 플랫폼의 **ID 생성기**
- 핵심 사용자:
    - 경기 종료 직후 직관 기록을 저장하며 ID를 발급받는 API 서버
    - 실시간 채팅 메시지를 저장·정렬하는 채팅 서버
    - 커서 기반 페이지네이션으로 최신 기록을 조회하는 클라이언트
- 핵심 기능:
    - 전역에서 겹치지 않는 ID 발급
    - 생성 시간 기준으로 대략적인 정렬 가능(k-sorted)
    - ID를 발급할 때 외부 네트워크 호출 없이 로컬에서 처리
- 제약사항:
    - **`signed BIGINT(64-bit)`** 를 사용한다.
        - 32비트 정수는 약 21억까지라 누적 데이터가 수십억 건으로 커지면 부족하다. `BIGINT`와 Java `long`은 64비트라 현재 규모에 충분하다.
        - Snowflake도 64-bit 정수 하나에 timestamp, worker id, sequence를 나눠 담는다.
            - sign 1 + timestamp 41(≈70년) + worker 10(1024) + sequence 12(ms당 4096)
        - JavaScript의 Number는 53-bit 정수까지만 정확하므로, 내부 DB는 BigInt로 두되 외부 JSON API에서는 ID를 **decimal string**으로 직렬화한다 (Java: `@JsonSerialize(using = ToStringSerializer.class)`)
    - 시간순 정렬이 가능해야 한다 (피드·채팅의 커서 페이지네이션에 사용)
        - MySQL에서는 Snowflake처럼 대체로 증가하는 PK가 B+Tree 끝부분에 모여 쓰기 지역성이 좋다.
        - UUIDv4처럼 랜덤한 PK는 B+Tree 여러 위치에 삽입돼 페이지 분할과 캐시 효율 측면에서 불리할 수 있다.
        - Cassandra에서는 partition key가 해시 분산되므로 이 장점이 그대로 적용되지는 않는다. Snowflake는 clustering key로 두어 파티션 내부 시간순 정렬에 활용한다.
    - 경기 종료 시간대에 쓰기가 폭증한다(burst): Peak 약 30,000 QPS, 포스트시즌 약 100,000 QPS
        - 직관 기록 남김, 채팅 기록 남김
        - 경기당 30만 건 : 30만건 * 5(하루 경기수) = 150만건 중 60% = 150만 * 0.6 / 30 = 대략 3만 QPS
    - 발급 지연이 저장 경로의 지연에 더해지므로 hot path에 외부 왕복이 없어야 한다.
        - id 발급 + 저장
    - 발급 서버는 여러 대이며 오토스케일로 증감한다
        - auto_increment step 다르게 증가하는 방법 사용 불가
    - 중복 ID는 허용하지 않는다.
        - PK가 겹치면 쓰기가 실패하거나 기존 데이터와 충돌할 수 있다.
- 제외할 범위
    - 직관 기록 저장소 자체 (6장 분산 KV)
    - 경기 일정·점수 조회 캐시 (5장)
    - 승률·랭킹 집계 로직
    - 보안 토큰·초대 코드처럼 예측 불가능성이 필요한 ID (별도 CSPRNG)
    - 계정·결제 등 강한 트랜잭션 PK (기존 MySQL AUTO_INCREMENT 유지 가능)

### 품질 우선순위

- 1순위: **전역 `유일성`** (같은 ID가 두 번 나오면 안 됨)
- 2순위: **`고가용성`·저지연** (로컬에서 발급하고, 일부 노드 장애가 전체 쓰기를 막지 않도록 함)
- 3순위: **시간순 `정렬` 가능성** (전역적으로 완벽한 순서까지는 필요하지 않음)
    - 서버 간 순서가 조금 섞이는 것은 허용한다.
- 허용 가능한 희생
    - 완벽한 단조 증가(strict monotonic)는 포기: 서버 간에는 대략 정렬(k-sorted)만 보장
    - ID의 연속성(빈 값 없이 1씩 증가)은 포기: 구간이 비어도 무방
    - ID의 예측 불가능성은 포기: 순차성이 노출되어도 됨(민감 데이터는 제외 범위)
    - 밀리초당 발급 상한(worker당 4096개) 초과 시 아주 짧은 대기 허용

### 규모

- 쓰기 QPS (ID 발급 수요)
    - 평균 수십~수백 QPS (경기 없는 시간대는 거의 0)
    - 경기 종료 시간대 Peak 약 `30,000 QPS`, 포스트시즌·이벤트 시 약 100,000 QPS
    - 채팅 메시지 발급까지 합산해도 총 Peak 수십만 QPS 수준
- 발급 노드 수: ID 발급 로직을 내장한 API/채팅 서버 수십~수백 대 (오토스케일)
- 하나의 ID가 감당해야 할 수명:
    - custom epoch 기준 41-bit ms → 약 `69.7`년
- 데이터 규모:
    - 직관 기록 시즌 약 2.2억 건, 누적 20~30억 건 (6장 기준)
    - 채팅·이벤트까지 포함하면 연 수십억 건 규모의 ID 발급
- 확인 질문
    - 가장 중요한 사용자 흐름은?
        - 경기 종료 직후 대량의 `직관 기록·채팅에 ID를 붙여 저장`하는 쓰기 흐름
    - 실시간 처리가 필요한가?
        - ID 발급은 즉시(마이크로초 단위) 응답이 필요하다. 외부 왕복은 허용하지 않는다.
    - 데이터 손실이나 중복을 허용할 수 있는가?
        - 중복 ID는 절대 불가(PK 충돌). 발급 실패 시 재시도로 흡수.
    - 일관성은 어느 수준까지 필요한가?
        - 전역 유일성은 강하게, 정렬은 서버 간 대략(k-sorted)만 보장.
    - 특정 기술이나 기존 인프라를 활용해야 하는가?
        - 저장소는 6장의 분산 KV(Cassandra)와 기존 MySQL. ID는 BIGINT PK로 양쪽에 모두 쓰인다.
        - Worker ID는 etcd/ZooKeeper의 lease로 동적으로 할당한다.
            - etcd: lease로 worker id를 확보하고 heartbeat로 갱신한다.
            - ZooKeeper: ephemeral node를 이용해 세션 수명과 worker id 할당을 묶을 수 있다.
            - StatefulSet ordinal도 후보지만, ID 하나 때문에 stateless API 서버에 stable Pod identity를 강제하게 되어 이번 설계에서는 사용하지 않는다.

## 2. 개략 설계안 제시 & 동의 구하기

중규모까지는 직관 기록과 채팅을 MySQL에 저장하고 `AUTO_INCREMENT`로 PK를 발급해도 충분하다.

하지만 저장소를 여러 노드나 샤드로 나누기 시작하면 이야기가 달라진다. 쓰기는 분산됐는데 ID만 한 DB에서 발급하면 그 DB가 다시 중앙 병목이 된다.

- 저장소를 늘려도 PK를 한 DB에서 발급하면 ID 요청은 계속 한곳에 몰린다.
- 중앙 ID 발급 DB에 장애가 나면 새로운 쓰기도 함께 막힌다.
- Cassandra에는 전역 `AUTO_INCREMENT`가 없어서 애플리케이션에서 PK를 만들어야 한다.
- 채팅이나 피드는 시간순 커서 조회가 필요하므로 생성 시간과 무관한 랜덤 ID는 활용도가 떨어진다.

### 후보 비교

| 방식 | 유일성 | 정렬 | 크기 | 조정 비용 | 한계 |
| --- | --- | --- | --- | --- | --- |
| Multi-master AUTO_INCREMENT (step=k) | O | 약함 | 64-bit | 서버 증감 시 step 재조정 | 서버 추가/축소가 어렵고 시간 정렬이 깨짐 |
| UUID v4 | O (사실상) | X (랜덤) | 128-bit | 없음 | 크고 랜덤 → 인덱스 지역성 나쁨, 정렬 불가 |
| Ticket Server (중앙 DB ID 발급) | O | O | 64-bit | 매 발급마다 중앙 왕복 | SPOF·병목, hot path 네트워크 왕복 |
| Snowflake (timestamp+worker+seq) | O | O (대략) | 64-bit | 부팅 시 worker id 1회 | 시계 의존, worker id 관리 필요 |
- **Multi-master**: 서버마다 `AUTO_INCREMENT`의 offset/step을 다르게 두는 방식(1,4,7… / 2,5,8…)
    - 노드 수가 바뀔 때 설정을 다시 맞춰야 하고, ID 값 자체가 생성 시간 순서를 자연스럽게 나타내지도 않는다.
- **UUIDv4**: 128-bit 랜덤 ID
    - 별도 조정 없이 각 서버에서 만들 수 있다는 점은 좋다. 하지만 이번 요구사항인 64-bit에 맞지 않고 시간순 정렬도 안 된다. MySQL B+Tree PK로 쓰면 삽입 위치도 랜덤하게 퍼진다.
- **Ticket Server(Flickr 방식)**: 중앙 DB에서 증가하는 ID를 발급한다.
    - 유일성과 순서를 보장하기는 쉽지만 모든 요청이 중앙 발급기를 거쳐야 한다.
    - 이중화하더라도 네트워크 왕복은 남고, 전체 발급량도 결국 Ticket Server가 감당할 수 있는 처리량에 묶인다.
- **Snowflake**: 시각+worker+시퀀스를 비트로 조합해 **각 서버가 로컬에서** 64-bit ID를 만든다.
    - 로컬에서 생성하므로 네트워크 왕복이 없고, 상위 비트가 시간이라 대략 정렬된다.

> 결론: 요구사항(64-bit, 시간 정렬, 조정 없는 고속 발급, 분산 저장소 PK)에는 **`Snowflake` 계열**이 가장 단순하고 적합하다.
> 

### Snowflake 비트 레이아웃 (64-bit)

<img width="822" height="233" alt="image" src="https://github.com/user-attachments/assets/411cc500-7700-469f-b9fb-99a16d3d3846" />

- sign bit (1): 항상 0, 양수 ID 보장 (BIGINT signed 호환)
- timestamp (41): custom epoch(서비스 런칭 시점) 이후 경과 밀리초 → 2^41 ms ≈ **69.7년**
- worker id (10): **flat namespace**, 최대 **1024개 발급 프로세스**
    - 국내에서 서버 100대 이상 필요하므로 data center(5 bit)를 사용하지 않았다.
- sequence (12): 같은 ms, 같은 worker 내 순차적으로 증가 → ms당 **4096개** (worker당 초당 약 409만 개)

### 개략적 추정

#### 발급 용량

worker 1개가 ms당 4096개, 초당 약 409만 개(4.09M / s). worker가 최대 1024개이므로 1024 * 409만 = 약 41.9억 / s 

야구보구 Peak(직관+채팅 수십만 QPS)는 worker 수 개면 충분하다. 

즉 **시퀀스 소진은 사실상 발생하지 않는다.**

#### 수명

```jsx
41-bit ms = 2^41 = 2,199,023,255,552 ms ≈ 69.7년
custom epoch = 2024-01-01 (서비스 런칭)
→ 약 2093년까지 사용 가능
```

epoch를 유닉스 0이 아니라 런칭 시점으로 잡아 41비트 수명을 최대한 확보한다.

- Go deeper
    - 가장 중요한 요청 흐름: 경기 종료 직후 대량 저장 시 각 서버가 로컬에서 ID를 즉시 발급
    - 가장 먼저 발생할 병목:
        - 발급이 아니라 저장 경로(6장 `Cassandra` 쓰기)
        - 같은 ms에 한 worker가 4096개 초과 시 다음 ms 대기
    - 단일 장애 지점: 중앙 ID 발급 DB를 제거(로컬 발급)
    - 읽기 확장 방식: ID 자체가 시간 정렬 → 커서 페이지네이션으로 읽기 최적화
    - 쓰기 확장 방식: 발급 노드(worker) 추가 = 발급 용량 선형 증가
    - 주요 실패 시나리오:
        - 시계 역행(clock skew), worker id 중복, 시퀀스 소진(대기해야함), 노드 재시작 시 id 재사용

## 3. 핵심 설계 결정 (Decision Log)

- Decision #1: 중앙 ID 발급(AUTO_INCREMENT / Ticket Server) 대신 `Snowflake` 로컬 발급을 채택
    - 해결하려는 문제:
        - ID 발급이 한 DB에 몰리면서 생기는 처리량 한계와 SPOF
        - Cassandra처럼 전역 `AUTO_INCREMENT`가 없는 저장소에서도 같은 방식으로 PK를 만들 수 있어야 함
        - ID 하나를 만들 때마다 중앙 서버를 거치지 않도록 함
    - 선택 이유:
        - 각 서버가 로컬에서 ID를 만들어 바로 저장 경로에 사용할 수 있다.
        - 발급 노드를 늘리면 중앙 채번기 없이 처리량을 늘릴 수 있다.
            - Multi-master AUTO_INCREMENT(step/offset)처럼 노드 수에 맞춰 설정을 다시 잡을 필요가 없다.
        - 한 발급 노드가 내려가도 다른 노드는 계속 ID를 만들 수 있다.
            - Ticket Server처럼 중앙 발급기 장애가 전체 쓰기를 막지 않는다.
    - 대안:
        - Multi-master AUTO_INCREMENT(step/offset)
        - Ticket Server(중앙 MySQL ID 발급)
        - 단일 RDB AUTO_INCREMENT 유지
    - 트레이드오프:
        - 시계에 의존하게 된다(시계 역행 대응 필요).
            - Decision #6
        - `worker id`를 유일하게 관리해야 한다.
        - 서버 간 완벽한 단조 증가는 포기한다.
    - 재검토 조건:
        - 발급량이 아주 작아 중앙 ID 발급으로 충분한 경우
        - 엄격한 gap-less 순번이 업무상 필수인 경우
            - ex) 세금계산서, 인보이스 번호
            - 번호 발급을 실제 저장과 같은 트랜잭션에 묶고, 직렬화
- Decision #2: UUID(128-bit) 대신 64-bit 정수 ID를 사용
    - 해결하려는 문제: PK 크기를 줄이면서 시간순 조회에도 쓸 수 있는 ID가 필요하다.
    - 선택 이유:
        - `BIGINT(8B)` 하나로 저장할 수 있어 UUID(16B)보다 PK와 인덱스 크기가 작다.
        - 상위 비트가 `timestamp`라 MySQL에서는 값이 대체로 증가하는 형태로 들어간다.
        - ID 자체를 채팅·피드의 시간순 커서로 활용할 수 있다.
    - 대안:
        - UUID v4(랜덤), UUID v7(시간 기반이지만 128-bit)
        - ULID(128-bit, 문자열)
    - 트레이드오프:
        - 128-bit보다 좁은 공간(worker 1024·ms당 4096) 안에서 설계해야 한다.
        - ID에서 순차성이 노출된다(민감 식별자엔 부적합 → 제외 범위).
    - 재검토 조건:
        - worker 수나 ms당 발급량이 64-bit 한계를 넘어서는 경우 → `UUIDv7` 검토
            - 크기가 커서 인덱스 페이지에 많이 안담김. 메모리 효율이 떨어진다.
            
            ```java
            [ 앞 48비트: 유닉스 밀리초 timestamp ][ 버전/변형 비트 ][ 나머지 ~74비트: 랜덤 ]
                 ↑ 시간순 정렬 담당              ↑ 유일성 담당(조정 없이)
            ```
            
- Decision #3: 비트 레이아웃 = sign(1) + timestamp(41) + worker(10) + sequence(12), custom epoch 사용
    - 해결하려는 문제: 64비트를 시간,노드,순번에 어떻게 배분할지
    - 선택 이유:
        - `41-bit` ms = 약 69.7년 수명(런칭 epoch 기준)으로 충분하다.
        - `10-bit` worker는 flat namespace(DC 분할 X)로 1024개 발급 프로세스를 수용한다.
        - `12-bit` sequence = ms당 4096개
    - 대안:
        - timestamp 42 / worker 8 / seq 13 등 다른 분할
        - worker 10-bit를 datacenter 5 + machine 5로 분할 (→ DC당 32대뿐이라 단일 DC 수백 대와 모순, 채택 안 함)
    - 트레이드오프:
        - worker 비트를 키우면 노드는 늘지만 ms당 발급 상한이 줄어든다(상호 배타).
        - custom epoch를 바꾸면 기존 ID와 시간 해석이 달라져 마이그레이션이 필요하다.
    - 재검토 조건:
        - 노드 수가 1024를 넘거나, 단일 worker ms당 4096개를 넘는 경우 재분할
- Decision #4: ID 생성기를 별도 서비스가 아니라 애플리케이션 내장 라이브러리로 배치
    - 해결하려는 문제: ID 생성기 때문에 쓰기 경로에 별도 네트워크 호출을 추가하지 않기
    - 선택 이유:
        - 내장 라이브러리면 `nextId()`가 프로세스 내부 호출로 끝난다.
        - 별도 ID 서비스의 처리량과 장애를 따로 운영할 필요가 없다.
        - 외부 조정은 서버 시작 시 worker id를 확보할 때만 필요하다.
    - 대안:
        - 독립 ID 발급 마이크로서비스(gRPC/HTTP)
            - 서버 따로 두기
        - 사이드카(sidecar) 방식
            - id 발급 서버를 같은 pod안의 다른 컨테이너에 둠, 로컬 통신
            - 프로세스간 통신(ipc)라서 함수 호출보다는 느림, pod마다 사이드카 관리 필요
    - 트레이드오프:
        - 발급 로직이 여러 언어/서버에 구현해야하고, 중복 배포된다(라이브러리 버전 관리 필요).
        - 각 노드가 유효한 worker id를 반드시 확보해야 한다.
    - 재검토 조건:
        - 다양한 언어 스택이 늘어 라이브러리 유지가 부담되면 사이드카/서비스화 검토
- Decision #5: Worker ID는 etcd/ZooKeeper lease로 할당하되, 만료 즉시 재사용하지 않는다 (fencing + quarantine/high-water mark)
    - 해결하려는 문제:
        - **lease가 만료됐다고 workerId를 바로 넘기면 기존 노드와 새 노드가 같은 번호를 동시에 쓸 수 있다.**
            - `zombie node`: coordinator에서는 죽은 것으로 보이지만 실제 프로세스는 살아 있는 경우다. 네트워크가 끊긴 사이 lease가 만료되고 새 노드가 같은 `workerId`를 받으면 충돌할 수 있다.
            - `process pause`: 긴 GC pause나 VM suspend 중 lease가 만료됐는데, 기존 프로세스가 깨어나 그대로 발급을 재개하는 경우이다.
            - `clock rollback`: 같은 workerId를 다시 쓰는 시점에 서버 시간이 과거 구간으로 돌아가 있으면 이전 timestamp 영역과 겹칠 수 있다.
    - 선택 이유
        - workerId lease는 서버를 시작할 때 확보하고, 실제 `nextId()` 호출에는 coordinator를 호출하지 않는다.
        - 실행 중에는 watchdog이 lease 상태를 확인하고, **갱신에 실패해 더 이상 유효하다고 볼 수 없으면 발급을 중단(fencing)** 한다.
        - 만료된 `workerId`는 즉시 재사용하지 않고 다음 중 하나로 안전성을 확보한다.
            - (a) **`quarantine window`**: 일정 시간 동안 workerId를 재할당하지 않고, 이전 holder가 사용했을 가능성이 있는 timestamp 영역을 충분히 지난 뒤 재사용한다.
            - (b) **worker별 `high-water mark`**: coordinator에 이전 holder가 사용한 안전한 timestamp 상한인 `last_safe_timestamp`를 기록하고, 새 holder는 `now > last_safe_timestamp`가 된 뒤에만 발급을 시작한다.
    - 대안:
        - 정적 설정으로 worker id 고정
            - 서버 수가 고정되어 있으면 단순하지만, 오토스케일 환경에서는 `workerId` 중복, 고갈·설정 관리 문제가 생기므로 채택하지 않는다.
        - lease 만료 즉시 재사용
            - `zombie node`나 `process pause`상황에서 기존 holder와 새 holder가 같은 workerId를 동시에 사용할 수 있으므로 채택하지 않는다.
    - 트레이드오프:
        - workerId 재사용까지 `quarantine` 지연이 발생할 수 있다.
        - coordinator에 lease 상태와, high-water mark 방식을 사용할 경우 worker별 timestamp 상태를 관리해야 한다.
        - etcd/ZooKeeper에 부팅 시 의존성이 생긴다. 다만 이미 workerId를 확보한 노드의 ID 발급 hot path에는 영향을 주지 않는다.
    - 재검토 조건
        - 노드 수가 소수이고 고정되어 정적 workerId 할당으로 충분한 경우
        - 이미 `StatefulSet`을 사용하는 구조이거나 별도 coordinator 운영 비용이 더 큰 경우
    - 참고:
        - 프로세스 로컬 `lastTimestamp`는 재시작 시 사라지므로 재사용 안전성을 메모리에만 의존하면 안 된다. high-water mark를 사용할 경우 coordinator에 상태를 남겨 재시작, 재할당 이후에도 과거 timestamp 영역 재사용을 막는다(Decision #6과 연동).
- Decision #6: 시계 역행(clock going backwards)은 감지 후 대기, 큰 역행은 발급 거부
    - 해결하려는 문제:
        - NTP 보정이나 VM migration/suspend 같은 상황에서 wall clock이 뒤로 갈 수 있다. 이때 이전에 사용한 timestamp를 다시 쓰면 ID가 겹칠 수 있다.
            - NTP는 서버 시간을 기준 시각에 맞추는 과정에서 clock을 조정한다.
            - VM은 이동이나 suspend/resume 과정에서 시각 보정이 발생할 수 있다.
    - 선택 이유:
        - 마지막으로 사용한 `lastTimestamp`를 기억하고, `now < lastTimestamp`이면 바로 발급하지 않는다.
        - 차이가 작으면 이전 timestamp를 지날 때까지 잠깐 기다리고, 차이가 크면 해당 노드의 발급을 중단한다.
        - NTP는 가능하면 `slew` 방식으로 맞춰 시간을 한 번에 뒤로 이동시키는 step 보정을 줄인다.
            - `slew`는 clock 값을 바로 바꾸는 대신 흐르는 속도를 조금 조정해 기준 시각에 맞추는 방식이다.
    - 대안:
        - 시계 역행 무시(중복 위험)
        - 논리 시계/타임스탬프 오라클 도입(복잡)
    - 트레이드오프:
        - 큰 역행 시 해당 노드는 일시적으로 발급 불가(다른 노드가 처리).
        - 대기 동안 발급 지연이 소폭 증가한다.
    - 재검토 조건:
        - 시계 인프라가 매우 안정적이어서 역행이 사실상 없는 경우 임계값 완화
    - 참고:
        - 프로세스 로컬 `lastTimestamp`는 재시작 시 소실된다. 재시작, worker id 재할당 후에도 과거 timestamp 재사용을 막으려면 coordinator의 worker별 high-water mark(Decision #5)와 함께 동작해야 한다.
- Decision #7: 같은 ms 내 sequence 소진(4096 초과) 시 다음 ms까지 대기
    - 해결하려는 문제: 같은 worker가 한 millisecond 안에서 12-bit sequence를 모두 사용한 경우
    - 선택 이유:
        - sequence `0~4095`를 모두 썼으면 다음 millisecond가 될 때까지 기다린 뒤 `sequence=0`부터 다시 시작한다.
        - 같은 `timestamp + workerId + sequence` 조합을 다시 쓰지 않기 위한 처리다.
        - 현재 예상 트래픽에서는 이 지점보다 API 처리나 저장소 쓰기가 먼저 병목이 될 가능성이 높다.
    - 대안:
        - sequence overflow 시 다른 worker로 넘김(복잡)
        - 초과분을 미래 ms로 당겨 발급(시간 왜곡)
    - 트레이드오프:
        - 극단적 burst의 아주 짧은 순간 발급이 다음 ms로 지연될 수 있다.
    - 재검토 조건:
        - 단일 worker에 발급이 과도하게 몰리면 worker 수 증설 또는 sequence 비트 확대
- Decision #8 (향후): Multi-datacenter/Region 확장과 ID 공간 관리
    - 해결하려는 문제: Multi-region으로 확장하거나 41-bit timestamp 수명에 가까워졌을 때 현재 레이아웃을 어떻게 바꿀지
    - 선택 이유:
        - 지금은 worker 10-bit를 region 구분 없이 flat namespace로 사용한다. Multi-region이 실제로 필요해지면 region 수와 region별 worker 수를 기준으로 비트를 다시 나누거나 새 layout을 도입한다.
        - 현재 64비트는 이미 모두 사용하고 있으므로 별도 예약 비트는 없다. epoch나 비트 구성을 바꿀 때는 새 레이아웃을 정의하고 버전을 외부 메타데이터나 마이그레이션 과정에서 구분한다.
    - 대안:
        - 단일 리전 유지, 고정 레이아웃
    - 트레이드오프:
        - DC/machine 분할을 바꾸면 기존 발급 ID와의 해석 호환을 관리해야 한다.
    - 재검토 조건:
        - 글로벌 사용자·다중 리전 요구가 실제로 생길 때
    - 참고:
        - 현재 요구(국내 중심, DAU 수백만)에는 Single Region + flat worker namespace로 충분하다. Multi-region은 향후 진화로 둔다.

### 비트 레이아웃과 생성 알고리즘

<img width="822" height="233" alt="image" src="https://github.com/user-attachments/assets/1357db90-ecbf-40fe-842e-1f5728a4883c" />

```java
synchronized long nextId() {
    long now = currentTimeMillis() - EPOCH;   // custom epoch

    if (now < lastTimestamp) {                 // 시계 역행 감지
        long drift = lastTimestamp - now;
        if (drift <= MAX_BACKWARD_MS) {
            now = waitUntil(lastTimestamp);    // 짧으면 대기
        } else {
            throw new ClockMovedBackwardException(drift); // 크면 거부
        }
    }

    if (now == lastTimestamp) {                // 같은 ms
        sequence = (sequence + 1) & 0xFFF;     // 12-bit mask (0~4095)
        if (sequence == 0) {                   // 4096개 소진
            now = waitNextMillis(lastTimestamp); // 다음 ms 대기
        }
    } else {
        sequence = 0;                          // 새 ms → 리셋
    }

    lastTimestamp = now;
    return (now << 22) | (workerId << 12) | sequence;
}
```

- 상위 비트가 시각이므로 서로 다른 ms의 ID는 **항상 시간순**으로 정렬된다.
- 같은 ms 안에서는 sequence로 순번을 매겨 유일성과 국소 정렬을 보장한다.
- worker id가 서로 다르면 같은 ms·같은 sequence라도 ID가 달라 **전역 유일**하다.

---

### 핵심 불변식 (Uniqueness Invariant)

`(timestamp, workerId, sequence)` 튜플이 유일하면 ID도 유일하다. 

1. 동시에 살아 있는 두 generator가 **같은 `workerId`를 쓰지 않는다**.
2. 동일 worker에서 **`timestamp`가 과거 값으로 되돌아가지 않는다**.
3. 동일 `(timestamp, workerId)` 안에서 **sequence를 중복 사용하지 않는다**.

| 불변식 | 보호 장치 |
| --- | --- |
| workerId 중복 금지 | etcd lease + lease-loss fencing + 재사용 quarantine/high-water mark |
| timestamp 재사용 금지 | clock rollback 감지(대기/거부) + coordinator high-water mark |
| sequence 중복 금지 | process-local 동기화 + overflow 시 다음 ms 대기 |

---

### Worker ID 할당과 부트스트랩

**부팅 시 유일 worker id 확보가** 필요하다.

```jsx
서버 부팅
  ↓
etcd/ZooKeeper에 worker id lease 요청
  ↓ 사용 가능한 id를 원자적으로 획득 (ephemeral/lease)
  ↓ 획득 실패 시 다음 id 재시도
  ↓ 주기적 lease 갱신 (heartbeat)
정상 종료·크래시 → lease 만료 → id 반납/재사용
```

- **유일한 workerId 확보**
    - 오토스케일로 서버가 증감하므로 `workerId`를 정적으로 설정하지 않고 etcd/ZooKeeper의 lease를 이용해 동적으로 할당한다.
    - lease 획득은 서버 부팅 시 이루어지므로 `nextId()`의 **hot path에는 coordinator 네트워크 왕복이 없다.**
- **Lease 유지와 fencing**
    - 실행 중에는 `heartbeat`를 통해 lease를 주기적으로 갱신한다.
    - generator는 watchdog으로 lease 상태를 감시한다.
    - lease를 갱신하지 못하거나 유효성을 잃었다고 판단하면 **즉시 ID 발급을 중단(fencing)** 한다.
    - 이를 통해 lease를 잃은 기존 서버와 새로운 holder가 동시에 같은 workerId로 발급하는 것을 방지한다.
- **WorkerId의 안전한 재사용**
    - lease가 만료되었다고 해서 해당 프로세스가 반드시 종료됐다는 뜻은 아니다. 네트워크 분리나 process pause로 기존 프로세스가 살아 있을 수 있기 때문이다.
    - 따라서 만료된 workerId를 즉시 다른 서버에 할당하지 않고 다음 중 하나를 사용한다.
        - **Quarantine window:** 일정 시간 동안 workerId를 격리한 뒤 재사용한다.
        - **High-water mark:** coordinator에 worker별 `last_safe_timestamp`를 기록하고, 새 holder는 `now > last_safe_timestamp`가 된 이후에 발급한다.

---

### **시계(Clock) 처리**

Snowflake는 timestamp를 ID의 일부로 사용하기 때문에 서버 시간이 뒤로 가면 이미 사용한 timestamp 구간을 다시 사용할 수 있다.

```
정상:  ... → t=100 → t=101 → t=102
역행:  ... → t=102 → t=100
                         ↑
                 기존 timestamp 재사용 위험
```

이를 막기 위해 다음과 같이 처리한다.

- NTP는 가능하면 `slew` 방식으로 보정해 시간을 갑자기 앞뒤로 변경하는 `step`을 줄인다.
- generator는 마지막으로 사용한 `lastTimestamp`를 기억한다.
- `now < lastTimestamp`이면 clock rollback으로 판단한다.
    - 차이가 작으면 `lastTimestamp`에 도달할 때까지 기다린다.
    - 차이가 크면 해당 노드에서 ID 발급을 중단한다.
- VM migration, suspend/resume 등으로 큰 시간 차이가 발생한 노드는 정상화되기 전까지 트래픽에서 제외한다.
- 재시작하면 메모리의 `lastTimestamp`가 사라지므로, workerId 재사용 시에는 Decision #5의 quarantine/high-water mark 정책으로 보완한다.

---

### **시퀀스 오버플로와 동시성**

같은 worker는 한 millisecond 안에서 12-bit sequence를 사용한다.

```
timestamp = 1000ms

sequence
0 → 1 → 2 → ... → 4094 → 4095
                              ↓
                       다음 요청은 대기
                              ↓
timestamp = 1001ms
sequence = 0부터 다시 시작
```

- sequence 범위는 `0~4095`이므로 한 worker가 같은 ms에 최대 4096개의 ID를 만들 수 있다.
- 4096개를 모두 사용하면 다음 millisecond가 될 때까지 기다린 뒤 `sequence=0`부터 다시 시작한다.
- `nextId()`는 여러 스레드에서 동시에 호출될 수 있으므로 timestamp와 sequence 변경을 임계 구역으로 보호한다.
    - 우선 `synchronized`로 구현한다.
    - 실제 측정에서 lock contention이 문제가 될 때 CAS 등의 방식을 검토한다.
- 다음 ms를 기다릴 때는 계속 CPU를 태우는 busy-spin보다는 짧은 spin/park 방식을 사용한다.
    - Busy-spin: 계속 확인하기
    - Spin / park: 조금 확인하다가 잠깐 쉬기

> 
> 
> 
> 현재 예상 트래픽에서는 worker 하나가 감당할 수 있는 발급량보다 실제 요청량이 훨씬 작기 때문에 sequence 소진보다는 저장소 쓰기가 먼저 병목이 될 가능성이 높다.
> 

| **상황** | **처리** |
| --- | --- |
| `now > lastTimestamp` | 새로운 ms이므로 `sequence = 0` |
| `now == lastTimestamp` | `sequence++` |
| sequence 4096개 소진 | 다음 ms까지 대기 후 `sequence = 0` |
| `now < lastTimestamp`, 차이가 작음 | `lastTimestamp`까지 대기 |
| `now < lastTimestamp`, 차이가 큼 | 해당 노드의 ID 발급 중단 |

### **장애 시 동작**

#### **발급 노드 장애**

ID는 각 노드에서 독립적으로 생성하므로 한 노드가 내려가도 다른 노드의 발급에는 영향이 없다.

해당 노드가 사용하던 workerId는 lease가 만료된 후 바로 재사용하지 않고 Decision #5의 `quarantine`/`high-water mark` 조건을 만족한 뒤 다시 할당한다.

#### **etcd 장애**

etcd는 `workerId`를 할당하고 lease를 관리하는 데 사용하며 `nextId()` 호출 경로에는 포함되지 않는다.

따라서 etcd에 장애가 나더라도 **유효한 lease를 보유하고 있다고 확인할 수 있는 동안에만(TTL이 남아있는 동안)** 기존 노드는 ID를 발급한다. 새로 시작하는 노드는 workerId를 받을 수 없으므로 ID generator를 시작하지 않는다.

다만 lease 갱신/유효성을 확인할 수 없는 상태가 지속되어 lease를 잃었다고 판단되면 기존 노드도 fencing하여 발급을 중단한다.

#### **시계 이상**

작은 clock rollback은 기다렸다가 다시 발급한다. 설정한 허용 범위를 넘는 rollback이 발생하면 해당 노드의 발급을 중단하고 정상화 후 다시 투입한다.

#### **노드 재시작**

재시작하면 메모리에 있던 `lastTimestamp`가 사라지므로 단순히 새 프로세스의 현재 시간만 보고 발급을 시작하지 않는다.

재할당받은 workerId의 `quarantine` 기간이 끝났거나, `now > last_safe_timestamp` 임을 확인한 뒤 ID 발급을 시작한다.

### **저장소 연동 (MySQL vs Cassandra)**

Snowflake ID는 대략 시간순으로 증가하지만, 이 특성이 저장소에서 그대로 물리적인 쓰기 지역성으로 이어지는지는 저장 구조에 따라 다르다.

#### **MySQL**

MySQL에서 Snowflake ID를 `BIGINT PRIMARY KEY`로 사용하면 ID가 대체로 증가하므로 새로운 레코드가 B+Tree의 오른쪽 영역에 추가된다.

```sql
PRIMARY KEY (id)
```

따라서 UUIDv4처럼 랜덤한 PK에 비해 page split이나 랜덤한 페이지 접근이 줄고, PK 기반 커서 페이지네이션도 단순하게 만들 수 있다.

```sql
SELECT *
FROM talk
WHERE id < ?
ORDER BY id DESC
LIMIT 50;
```

단, 여러 worker가 동시에 ID를 생성하므로 Snowflake ID가 전역적으로 완벽한 단조 증가를 보장하는 것은 아니다. 같은 시간대의 ID가 약간 섞일 수 있지만 전체적으로는 시간순에 가깝게 정렬된다.

#### **Cassandra**

Cassandra에서는 Snowflake ID를 단독 partition key로 사용하는 방식은 적합하지 않다.

```sql
-- 사용하지 않음
PRIMARY KEY (snowflake_id)
```

partition key는 partitioner를 통해 token으로 변환되어 여러 노드에 분산되므로, Snowflake ID가 시간순이라고 해서 시간상 가까운 데이터가 같은 노드나 같은 파티션에 저장되는 것은 아니다.

```java
snowflake_id
     ↓
Murmur3 hash
     ↓
token
     ↓
담당 Cassandra 노드 결정
```

Partition Key는 해시되어 저장 노드가 결정되므로 Snowflake ID를 Partition Key로 사용해도 시간순 저장 효과를 얻을 수 없다. 

또한 Cassandra는 전체 파티션을 대상으로 전역 범위 조회를 하는 구조가 아니다.

```sql
WHERE snowflake_id < ?
ORDER BY snowflake_id DESC
```

따라서 **조회 패턴을 먼저 정하고 partition key를 설계한 뒤, Snowflake ID를 clustering key로 사용**한다.

```sql
-- 경기별 채팅
PRIMARY KEY ((game_id, bucket), snowflake_id)

-- 사용자의 시즌별 직관 기록
PRIMARY KEY ((member_id, season), snowflake_id)
```

`(game_id, bucket)` 등을 Partition Key로 사용하고, Snowflake ID는 Clustering Key로 두어 **같은 파티션 안에서 시간순 정렬과 페이지네이션**에 활용한다.

- 파티션 키 : 데이터를 어느 파티션(**Cassandra가 데이터를 묶어서 저장하고 조회하는 기본 단위)**에 넣을지
- 클러스터링 키 : 그 파티션 안에서 데이터를 어떤 순서로 둘지

```
Partition Key
(game_id, bucket)
(member_id, season)

→ 어느 파티션에 저장할지 결정
→ 데이터 분산 단위

Clustering Key
snowflake_id

→ 파티션 내부 정렬
→ 시간순 조회 / cursor pagination
```

예를 들어 경기 채팅은 특정 bucket 안에서 다음과 같이 조회할 수 있다.

```sql
WHERE game_id = ?
  AND bucket = ?
  AND snowflake_id < ?
ORDER BY snowflake_id DESC
LIMIT 50;
```

즉 Snowflake의 시간 정렬 특성은 Cassandra 전체의 물리 배치를 순차적으로 만드는 데 사용하는 것이 아니라, **같은 partition 내부에서 시간순 정렬과 pagination을 만드는 데 사용한다.**

### **확장 방식**

#### **발급 노드 확장**

각 worker가 독립적으로 ID를 생성하므로 발급 노드를 추가하면 전체 발급 처리량을 늘릴 수 있다.

```
worker 1 ─┐
worker 2 ─┼─→ 각자 nextId()
worker 3 ─┘
```

현재 10-bit worker 공간에서는 최대 1024개의 worker ID를 사용할 수 있다.

다만 실제 처리량이 worker 수에 정확히 비례한다고 단정하기보다는, **ID 생성 자체는 수평 확장이 가능하다**고 표현하는 편이 정확하다. 

> 실제 시스템에서는 API 처리량이나 저장소 쓰기가 먼저 병목이 될 수 있다.
> 

#### **단일 worker의 sequence 한계**

한 worker는 같은 millisecond에서 12-bit sequence를 사용하므로 최대 4096개의 ID를 생성한다. 이 한계에 자주 도달한다면 우선 트래픽을 여러 worker에 분산한다.

```
특정 worker에 요청 집중
        ↓
트래픽 분산 / worker 증설
        ↓
그래도 부족
        ↓
worker / sequence 비트 재검토
```

sequence 비트를 늘리면 worker나 timestamp에 사용할 비트가 줄어들기 때문에 단순히 sequence만 확장할 수는 없다.

#### **Multi-region 확장**

현재 10-bit worker 영역은 region을 구분하지 않는 **flat namespace**로 사용한다.

```
10-bit workerId
→ 0 ~ 1023
```

Multi-region이 실제로 필요해지면 region 수와 region별 worker 수를 기준으로 비트를 다시 나누는 방법을 검토한다.

```
2-bit region + 8-bit worker

region : 4개
worker : region당 256개
```

또는 기존 ID와의 호환성을 유지해야 한다면 기존 레이아웃을 바로 변경하기보다 **새로운 ID layout/version을 도입하는 방식**을 검토한다.

#### **Timestamp 수명**

41-bit millisecond timestamp는 약 69.7년을 사용할 수 있다.

```
custom epoch
     ↓
41-bit timestamp
     ↓
약 69.7년
```

41-bit timestamp의 수명에 가까워지면 새로운 epoch/비트 레이아웃을 정의하고, 저장소나 메타데이터에서 ID layout version을 구분하는 마이그레이션을 진행한다.

- Go deeper
    - CPU / Memory / Disk IO / Network
        - 발급은 CPU·메모리만 사용(디스크·네트워크 없음)
    - Connection / Lock / Queue 적체
        - worker당 임계 구역 락 경합(규모상 미미)
    - 중복 / 유실 / 순서 보장
        - 중복: worker id 유일 + 시계 단조로 방지
        - 순서: 같은 노드는 단조, 서버 간은 대략 정렬(k-sorted)
    - Retry / Timeout / Backpressure
        - 발급 실패(시계 대폭 역행) 시 상위에서 재시도/타 노드 라우팅
    - Partitioning / Replication / Failover
        - worker id 공간이 자연스러운 파티션, 조정 서비스만 HA 필요

## 5. 운영과 마무리

### 핵심 설계 요약

- 중앙 ID 발급(AUTO_INCREMENT/Ticket Server) 대신 **`Snowflake` 로컬 발급** 채택
- 64-bit 레이아웃: sign(1) + timestamp(41) + worker(10) + sequence(12), custom epoch(런칭 시점)
- ID 생성기는 **각 서버 내장 라이브러리** → hot path에 조정, 왕복 없음
- Worker id는 부팅 시 **etcd/ZooKeeper lease**로 유일 할당·재사용
- 시계 역행은 대기/거부 정책으로 유일성 보호, 시퀀스 소진은 다음 ms 대기
- 상위 비트가 시각이라 **대략 시간 정렬** → 채팅·피드 커서에 적합

### 주요 병목

- 저장 경로(6장 Cassandra 쓰기)
- 단일 worker의 ms당 4096 상한(극단 burst)
- 부팅 시 worker id 조정 서비스 의존
- worker당 임계 구역 락 경합(규모상 미미)

### 주요 트레이드오프

- 조정 없는 고속 발급을 얻지만 **시계에 의존**한다.
- 64-bit로 저장·정렬 효율을 얻지만 worker/seq 공간이 제한된다.
- 서버 간 완벽한 단조 증가를 포기하고 대략 정렬(k-sorted)만 보장한다.
- 시계 대폭 역행 시 정확성을 위해 해당 노드의 가용성을 잠시 희생한다.

### Metrics / Logs / Traces

- 발급 QPS(노드별/worker별)
- 시계 역행 감지 횟수·폭, 발급 거부(예외) 횟수
- 시퀀스 소진(다음 ms 대기) 발생률
- worker id lease 획득/갱신/만료 이벤트
- 발급 latency(p99, 마이크로초), NTP offset

### 장애 감지

- 동일 worker id 중복 사용(치명적 알람)
- 시계 역행·NTP offset 급증
- 시퀀스 소진 빈발(특정 worker 과부하 신호)
- lease 만료·재획득 실패 증가

### 복구 방법

- worker id 중복 감지 시 해당 노드 격리·재부팅으로 id 재임대
- 시계 이상 노드는 트래픽에서 빼고 NTP 재동기 후 복귀
- 조정 서비스 장애 시 쿼럼 복구, 기존 노드는 발급 지속

### 규모가 10배 증가하면

발급량이 수백만 QPS로 늘어도 발급기는 여유롭다(이론 41.9억/s). 실제로 먼저 확인할 것:

```jsx
저장 경로(Cassandra)가 쓰기 폭증을 견디는가? (6장)
특정 worker에 발급이 몰려 ms당 4096에 근접하는가?
Multi-region으로 worker 공간을 나눠야 하는가?
```

우선 적용:

1. 발급 노드(worker) 증설 : 선형 확장
2. region/worker 비트 재분할(layout version)로 Multi-region 수용
3. 필요 시 sequence/worker 비트 재분할(레이아웃 버저닝)
4. 저장 경로 병목 해소(6장 확장 전략과 연동)

### 추가로 검토할 내용

- 재시작·컨테이너 재스케줄 시 worker id 재사용 안전성 테스트(장애 주입)
- NTP slew vs step, VM suspend/이주 환경에서의 시계 점프 격리
- UUIDv7과의 비교 재검토(다언어 스택 확대 시)
- ID에서 노출되는 순차성이 문제되는 도메인 식별(민감 식별자 분리)
- epoch 고갈(수십 년)·비트 재분할 마이그레이션 계획

- 1) 문제 정의 (40초)
    
    "야구보구는 경기 종료 직후 직관 기록과 채팅이 초당 수만 건씩 몰립니다. 지금은 PK를 MySQL AUTO_INCREMENT로 뽑는데, 직관 기록을 분산 저장소로 옮기면 전역 AUTO_INCREMENT가 없어 애플리케이션이 직접 PK를 만들어야 합니다. 그래서 조정 없이 빠르고, 시간순으로 정렬되는 64비트 유일 ID가 필요합니다."
    
- 2) 후보 비교와 선택 (70초)
    
    "방법은 네 가지를 봤습니다. Multi-master AUTO_INCREMENT는 서버 증감 때 step을 다시 잡아야 하고 시간 정렬이 깨집니다. UUID는 조정이 없지만 128비트에 랜덤이라 인덱스 지역성이 나쁘고 정렬이 안 됩니다. Ticket Server는 중앙 DB가 ID 발급해서 유일·정렬은 되지만 매 발급이 네트워크 왕복이고 단일 장애점입니다. Snowflake는 각 서버가 로컬에서 시각·워커·시퀀스를 비트로 조합해 만듭니다. 64비트에 시간 정렬이 되고 발급에 왕복이 없어서, 비교한 후보 중에서는 Snowflake 계열이 요구사항과 가장 잘 맞아서 이걸 택했습니다."
    
- 3) 구조 (70초)
    
    "64비트를 sign 1, timestamp 41, worker 10, sequence 12로 나눴습니다. timestamp는 런칭 시점을 기준으로 한 밀리초라 41비트로 약 70년을 씁니다. worker 10비트로 노드 1024개, sequence 12비트로 밀리초당 4096개, 워커당 초당 약 409만 개를 발급합니다. id는 timestamp를 22비트, worker를 12비트 시프트해서 OR로 합칩니다. 상위 비트가 시각이라 서로 다른 밀리초의 ID는 항상 시간순으로 정렬됩니다."
    
- 4) 어려운 지점 두 개 (60초)
    
    "첫째, 시계입니다. Snowflake는 시각이 앞으로만 간다고 가정하는데, NTP 보정으로 시계가 뒤로 가면 과거 timestamp로 중복이 납니다. 그래서 마지막 발급 시각을 기억하고, 소폭 역행이면 그 시각까지 기다렸다 발급하고, 대폭이면 발급을 거부해 잘못된 ID를 막습니다. 둘째, worker id 유일성입니다. 오토스케일 환경이라 부팅할 때 etcd나 ZooKeeper에서 lease로 유일한 id를 받고, 죽으면 만료돼 회수·재사용합니다. 이건 발급 경로가 아니라 부팅 때 한 번만 조정합니다."
    
- 5) 야구보구 연결 + 마무리 (40초)
    
    "실제로 채팅에는 이미 clientMessageId라는 UUID 멱등키가 있는데, 이건 클라이언트가 재시도 멱등성을 위해 만드는 거라 서버 ID 발급과는 목적이 다릅니다. Snowflake는 서버 PK를 대체하고, clientMessageId는 그대로 둡니다. Snowflake로 바꾸면 id 자체가 시간 정렬돼서 커서 페이지네이션도 단순해집니다. 병목은 발급이 아니라 저장 경로라, 발급기는 노드만 늘리면 선형으로 확장됩니다."
    

## ❓ 예상 꼬리질문 Q&A

- Q. UUID로 충분하지 않나요? 왜 Snowflake인가요?
    - UUIDv4는 128비트에 랜덤이라 BIGINT에 안 들어가고, 무작위라 인덱스 append locality가 나빠 쓰기 폭증에 불리하며 시간 정렬이 안 됩니다.
    - 야구보구는 64비트 PK·시간 정렬·append 폭증이 핵심 요구라 Snowflake가 맞습니다.
    - 다만 워커 수나 발급량이 64비트를 넘어서면 128비트지만 시간 정렬되는 UUIDv7을 재검토합니다.
- Q. 시계가 뒤로 가면 정말 중복이 안 나나요?
    - 마지막 발급 timestamp를 기억해, 현재 시각이 그보다 작으면 소폭은 대기 후 발급, 대폭은 발급을 거부합니다.
    - NTP는 급격한 step 보정 대신 slew(점진 보정)로 운영해 역행 폭 자체를 줄입니다.
    - 거부된 노드의 트래픽은 정상 노드가 흡수하므로 전체 가용성은 유지됩니다. 정확성을 가용성보다 우선한 선택입니다.
- Q. 같은 밀리초에 4096개를 넘으면요?
    - 한 worker에서 sequence `0~4095`를 모두 사용하면 다음 밀리초까지 기다린 뒤 0부터 다시 시작합니다.
    - 현재 트래픽에서는 거의 닿지 않는 한계지만, 반복해서 발생한다면 먼저 worker 수와 트래픽 분산 상태를 확인합니다.
- Q. 죽은 줄 알고 lease가 만료됐는데 실제 노드는 살아 있으면요? (zombie node)
    - lease 만료 ≠ 노드 종료입니다. 네트워크 분리면 두 노드가 같은 worker id를 쓸 위험이 있습니다.
    - 그래서 lease를 잃은 generator는 **즉시 발급을 fencing(중단)** 하고, 만료된 id는 **즉시 재사용하지 않습니다**.
    - 재사용은 **quarantine window** 이후, 또는 coordinator의 worker별 **high-water mark**(`now > last_safe_timestamp`)를 넘긴 뒤에만 허용합니다.
    - 프로세스 로컬 `lastTimestamp`는 재시작 시 사라지므로, high-water mark를 coordinator에 남겨 재시작·재할당 후에도 timestamp 역행을 막습니다.
- Q. 별도 ID 서비스로 빼는 게 낫지 않나요?
    - 별도 서비스로 만들면 모든 쓰기 요청에 ID 발급용 네트워크 호출이 하나 더 생깁니다.
    - 지금은 라이브러리로 넣어 `nextId()`를 로컬에서 처리하고, 외부 조정은 worker id를 받을 때만 하도록 했습니다.
    - 언어가 많아져 라이브러리 관리 비용이 커지면 그때 사이드카나 별도 서비스로 분리하는 편이 낫습니다.
- Q. clientMessageId가 이미 유일한데 Snowflake가 왜 또 필요한가요?
    - clientMessageId는 클라이언트가 재시도 멱등성을 위해 만드는 UUID고, DB의 UNIQUE로 중복을 막는 용도입니다.
    - 레코드의 PK·정렬 키로 쓰기엔 128비트에 랜덤이라 부적합합니다.
    - 서버 PK 발급(정렬·분산 저장)과 클라이언트 멱등키는 목적이 달라 둘을 함께 씁니다.
- Q. ID에 시각이 노출되는데 보안 문제 없나요?
    - 순차성이 노출돼도 되는 내부 식별자(직관 기록·채팅 PK)에만 씁니다.
    - 초대 코드·보안 토큰처럼 예측 불가능성이 필요한 값은 별도 CSPRNG로 만들고 Snowflake를 쓰지 않습니다(설계 범위에서 제외).
- Q. Snowflake ID를 JSON으로 그대로 내려도 되나요?
    - JavaScript 클라이언트가 있다면 숫자보다는 문자열로 내려주는 편이 안전합니다. Snowflake ID는 `2^53 - 1`을 넘을 수 있어서 `Number`로 받으면 값이 달라질 수 있습니다.
    - DB와 서버 내부에서는 signed `BIGINT`/`long`을 쓰고, 외부 JSON에서는 **decimal string**으로 직렬화합니다 (Java: `@JsonSerialize(using = ToStringSerializer.class)`).
- Q. Cassandra에 Snowflake를 PK로 쓰면 시간순 조회가 쉬워지나요?
    - `PRIMARY KEY(snowflake_id)`로 두는 것만으로는 그렇지 않습니다. partition key는 해시되어 저장 위치가 정해지기 때문에 가까운 Snowflake ID가 같은 파티션에 모이지 않습니다.
    - `(game_id, bucket)` 같은 값을 partition key로 두고 `snowflake_id`를 **clustering key**로 사용해, 같은 파티션 안에서 시간순 조회와 pagination에 활용합니다.
