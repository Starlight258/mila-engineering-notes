# 알림 시스템

- 대상: 야구 직관 인증 플랫폼의 알림 시스템

- 질문: 야구보구는 응원팀 경기의 시작, 득점, 역전, 종료를 구독자에게 푸시로 보낸다고 가정한다.
경기 5개가 비슷한 시각에 끝나면 몇 분 안에 수백만 건을 한꺼번에 발송해야 한다. 

**이때 중복 발송을 줄이고 사용자 설정을 지키면서 버스트를 처리하려면 발송 경로를 어떻게 설계할까?**

> **핵심 문제:** 중복 발송과 알림 누락을 줄이면서, 순간적으로 몰리는 트래픽과 사용자의 알림 설정을 처리하기

> **설계 원칙:** 내부 메시지 전달은 `at-least-once` 방식으로 처리한다. 장애가 발생하면 작업을 재시도해 알림 누락을 줄이고, `(event_id, device_token)`을 `멱등 키`로 사용해 같은 이벤트가 같은 기기에 중복 처리되지 않도록 한다. 
다만 외부 푸시 서비스 호출까지 포함한 `exactly-once` 처리는 보장하지 않는다. (이벤트의 특성에 따라 알림 누락과 중복 발송 중 어느 쪽을 감수할지 정한다.)

> **규모 가정:** 아래 숫자는 야구보구의 실제 지표가 아니라 대규모 트래픽을 가정해 잡은 설계용 값이다.

---

## 1. 문제 정의 & 설계 범위 확정

- 서비스: **야구보구 경기 이벤트 알림**
    - 경기 시작, 득점, 역전, 종료 이벤트를 구독자에게 푸시로 전달한다.
- 사용자
    - 앱 사용자: 응원팀이나 특정 경기를 구독하고, 받을 이벤트와 방해금지 시간을 설정한다.
    - 운영자: 발송 현황을 확인하고 문제가 생기면 발송을 중단한다.
- 핵심 기능
    - 팀·경기 구독 및 알림 설정
    - 디바이스 토큰 관리
    - 경기 이벤트 수신과 중복 판별
    - 구독자 조회, 사용자 설정 필터링, 발송 작업 생성
    - APNs·FCM 발송과 실패 재시도
    - 발송 결과 기록
- 제외할 범위
    - 마케팅 알림과 사용자 세그먼트 기능
    - SMS·카카오 알림톡 등 푸시 외 채널
    - 개인화·추천·다국어 처리
    - 경기 스코어를 생성하는 외부 피드의 내부 구현

- 제약사항
    - APNs와 FCM은 외부 서비스이므로 처리량과 장애를 직접 통제할 수 없다.
    - 이미 발송된 푸시는 회수할 수 없다.
    - 스코어 피드에서 같은 이벤트가 중복되거나 정정되어 들어올 수 있다.
    - 여러 경기의 이벤트가 비슷한 시각에 발생하면 발송량이 순간적으로 몰린다.
    - 이벤트 종류와 방해금지 시간 등 사용자의 알림 설정을 반영해야 한다.

### **품질 우선순위**

- 1순위: `오발송과 중복을 줄이는 것`
    - 구독하지 않았거나 알림을 끈 사용자에게는 보내지 않는다.
    - 내부 재처리로 발생하는 중복은 멱등 처리로 처리한다.
- 2순위: `적시성`
    - 이벤트 발생부터 발송까지 p95 30초를 목표로 한다.
- 3순위: `처리량`
    - 여러 경기가 동시에 끝나는 버스트를 처리할 수 있어야 한다.
- 허용 가능한 범위
    - 초 단위 실시간성은 요구하지 않는다.
    - 모든 사용자에게 동시에 도착할 필요는 없으며 수십 초의 차이는 허용한다.
    - 외부 푸시 서비스까지 포함한 `exactly-once` 전달은 보장하지 않는다.

### **내구성 정의 (SLO)**

- 수신 API가 `202 Accepted`를 반환한 이벤트는 단일 노드 장애로 유실되지 않아야 한다.
    - 서버가 클라이언트의 요청을 받아들였으나, **아직 처리가 완료되지 않았음**
- `202`는 이벤트가 durable하게 기록된 이후에만 반환한다.
- 실제 기기 도착 여부는 외부 푸시 서비스에 의존하므로 시스템이 직접 보장하지 않는다.

### **규모**

- 알림 허용 기기: `200만`
- 경기: 하루 `5경기`
- 경기당 알림 이벤트: 약 `12건` → 하루 약 `60건`
- 이벤트당 평균 대상: `40만 기기`
- 하루 총 발송: 약 `2,400만 건`
- 이벤트 1건을 30초 안에 처리: 약 `13,000 발송/s`
- 5경기 종료가 겹쳐 200만 건을 60초 안에 처리: 약 `33,000 발송/s`

평균 수신 QPS는 낮지만 이벤트 하나가 수십만 건의 발송으로 확장된다. 따라서 수신 API보다 **fan-out 이후의 순간 처리량이 중요하다.**

- 확인 질문
    - 가장 중요한 흐름은? → 경기 이벤트 하나가 수십만 기기로 전달되는 경로
    - 실시간 처리가 필요한가? → 초 단위 실시간은 아니며 p95 30초를 목표로 함
    - 중복을 허용하는가? → 내부 재처리 중복은 줄이되 외부 공급자까지 exactly-once는 보장하지 않음
    - 어떤 사용자 설정을 반영하는가? → 이벤트 종류, 채널, 방해금지 시간

## **2. 개략 설계안 제시 & 동의 구하기**

경기 이벤트 하나가 수십만 명의 구독자에게 전달될 수 있으므로, 이벤트를 받은 요청에서 모든 푸시를 바로 발송하지 않는다. 이벤트를 큐에 저장한 뒤, 별도 Worker가 구독자를 조회하고 푸시를 비동기로 발송한다.

!image.png

### **발송 경로**

!image.png

1. `Event Ingest API`가 경기 이벤트를 받고, `(game_id, event_type, seq)`로 중복 이벤트인지 확인한다.
2. 새로운 이벤트라면 `event_id`를 발급하고 `Event Queue`에 안전하게 기록한 뒤 `202`를 반환한다.
3. `Fan-out Worker`가 이벤트를 가져와 구독자를 조회하고 사용자 설정을 적용해 실제 발송 대상을 만든다.
4. 발송 대상을 `chunk` 단위로 나눠 채널별 `Delivery Queue`에 넣는다.
    - 큐 메세지를 과도하게 늘리지 않기 위해 chunk 단위로 큐에 넣는다.
5. `Sender Worker`가 발송 직전에 중복 여부를 확인한 뒤 APNs 또는 FCM으로 전송한다.
6. 일시적인 실패는 재시도하고, 무효 토큰은 폐기하며, 처리할 수 없는 실패는 `DLQ`로 보낸다.
7. 발송 결과를 저장하고 성공률과 실패율은 비동기로 집계한다.

```
경기 이벤트
    ↓
Event Ingest API
    ↓
Event Queue
    ↓
Fan-out Worker
    ↓
구독자 조회 + 사용자 설정 필터
    ↓
채널별 Delivery Queue
    ↓
Sender Worker
    ↓
APNs / FCM
```

- **Fan-out Worker**
    - 역할: **누구에게 보낼지 결정**
    - 구독자를 조회하고 사용자 설정을 확인해 발송 대상을 만든다.
    - 구독자가 많아 조회·필터링이 느려지면 Worker를 늘려 병렬 처리한다.
- **Sender Worker**
    - 역할: **선정된 대상에게 실제 알림 발송**
    - `Delivery Queue`에서 작업을 가져와 APNs/FCM으로 전송한다.
    - 발송 작업이 쌓이면 Worker를 늘려 병렬 처리한다.
    - 단, APNs/FCM의 처리량 한도 내에서 확장한다.

### **후보 비교**

- **수신 요청에서 바로 발송**: 구조는 단순하지만 이벤트 하나가 수십만 건으로 늘어나면 요청 시간이 길어지고, 중간 실패 시 재처리해야한다.
- **발송 건을 모두 개별 메시지로 큐에 저장**: 건별 처리는 쉽지만 이벤트 하나만으로 수십만 개의 메시지가 만들어져 fan-out이 발생한다.
- **선택: 이벤트 큐 + chunk 단위 fan-out + 채널별 발송 큐**: 이벤트를 먼저 받아두고 fan-out과 발송을 분리한다. chunk 단위로 작업을 나눠 실패를 줄이고, 채널별 발송은 독립적으로 확장한다.

### **주요 컴포넌트**

- `Event Ingest API`: 이벤트 수신과 중복 판별
- `Event Queue`: 수신과 fan-out 분리
- `Fan-out Worker`: 구독자 조회, 설정 필터링, chunk 생성
- `Subscription / Preference Store`: 구독 및 알림 설정 조회
- `Delivery Queue`: 발송 작업 대기
- `Sender Worker`: APNs·FCM 발송과 재시도
- `Dedup Store`: 내부 재처리로 인한 중복 발송 억제
- `Notification Log`: 발송 결과 기록

### **개략적 추정**

- 이벤트 1건: `40만 기기` → 30초 처리 시 약 `13,000/s`
- 5경기 동시 종료: `200만 건` → 60초 처리 시 약 `33,000/s`
- chunk를 `1,000건`으로 시작하면 이벤트당 약 `400개`, 동시 종료 시 약 `2,000개`의 작업으로 나뉜다.

구독자 수가 늘면 Fan-out Worker를, 발송량이 늘면 Sender Worker를 각각 확장할 수 있다.

## 3. 핵심 설계 결정 (Decision Log)

- Decision #1: **대규모 발송을 `비동기`로 처리하기 위해 Event Queue 도입**
    
    !image.png
    
    - **문제**
        - 경기 이벤트 하나가 평균 40만 건의 발송으로 늘어난다.
        - 수신 요청에서 구독자 조회와 푸시 발송까지 처리하면 요청 시간이 길어지고, 중간에 실패했을 때 어디까지 처리했는지 관리하기 어렵다.
    - **선택**
        - `Event Ingest API`는 이벤트를 검증하고 중복 여부를 확인한 뒤 `Event Queue`에 기록한다.
        - 큐에 안전하게 기록되면 `202 Accepted`를 반환하고, 이후 fan-out과 발송은 Worker가 비동기로 처리한다.
    - **선택한 이유**
        - 발송이 밀려도 이벤트 수신은 계속할 수 있다.
        - 수신과 대량 발송의 처리량 차이를 큐가 흡수할 수 있다.
        - fan-out과 발송을 수신 API와 별도로 확장할 수 있다.
    - **트레이드오프**
        - `202`는 발송 완료가 아니라 이벤트가 처리 대상으로 접수됐다는 의미로 사용된다.
        - 큐가 추가되므로 적체량과 처리 지연을 모니터링해야 한다.
- Decision #2: **재처리 중복을 줄이기 위해 단계별 멱등 처리 도입**
    
    !image.png
    
    - **문제**
        - 스코어 피드가 같은 경기 이벤트를 다시 보낼 수 있다.
        - 내부 큐를 `at-least-once`로 처리하면 Worker 장애나 재시도로 같은 발송 작업이 다시 실행될 수 있다.
    - **선택**
        - 수신 단계에서는 `(game_id, event_type, seq)`를 기준으로 같은 이벤트인지 확인한다.
            - 같은 이벤트가 또 들어왔는지 확인
            - 이미 처리한 이벤트라면 새 이벤트를 만들지 않고 기존 `event_id`를 사용한다.
        - 발송 단계에서는 `(event_id, device_token)`을 멱등 키로 사용해 같은 이벤트가 같은 기기에 다시 발송되는 것을 줄인다.
            - 이벤트를 해당 기기에 이미 보냈는지 확인
    - **선택한 이유**
        - 수신 중복과 발송 중복은 발생하는 위치와 원인이 다르므로 각각 다른 키로 처리하는 편이 단순하다.
    - **트레이드오프**
        - APNs·FCM 호출과 내부 상태 저장을 하나의 트랜잭션으로 묶을 수 없기 때문에 외부 공급자까지 포함한 `exactly-once`는 보장하지 않는다.
        - 공급자 호출 결과를 확인하지 못한 경우에는 이벤트 종류에 따라 재전송 여부를 결정한다.
- Decision #3: **fan-out의 재처리 범위를 줄이기 위해 chunk 단위 처리 도입**
    
    !image.png
    
    - **문제**
        - 발송 대상 40만 건을 하나의 작업으로 묶으면 Worker 장애 시 재처리해야 하는 범위가 너무 커진다.
        - 반대로 기기별로 작업을 만들면 이벤트 하나당 수십만 개의 Queue 메시지가 생성되어 Queue의 처리 부담이 커진다.
    - **선택**
        - 발송 대상을 일정 크기의 `chunk`로 나눠 `Delivery Queue`에 넣는다.
        - 초기값은 chunk당 1,000건으로 두어 이벤트 하나를 약 400개의 작업으로 나눈다.
        - 실패한 작업은 해당 chunk만 다시 처리한다.
    - **선택한 이유**
        - 큐 메시지 수를 과도하게 늘리지 않으면서 재처리 범위를 제한할 수 있다.
        - 여러 Worker가 서로 다른 chunk를 가져가 병렬로 처리할 수 있다.
    - **트레이드오프**
        - chunk가 크면 큐 메시지는 줄지만 실패 시 다시 처리하는 범위가 커진다.
        - chunk가 작으면 재처리 범위는 줄지만 큐 메시지 수가 늘어난다.
        - 1,000건은 초기값이며 실제 큐 지연과 재처리량을 보고 조정한다.
- Decision #4: **팀별 구독자를 빠르게 조회하기 위해 조회 전용 테이블(SubscriptionByTeam) 도입**
    
    !image.png
    
    - **문제**
        - 경기 이벤트가 발생하면 해당 팀을 구독한 사용자를 빠르게 조회해야 한다.
        - 인기 팀은 구독자가 수십만 명까지 늘어날 수 있어 하나의 파티션에 데이터와 조회 부하가 집중될 수 있다.
    - **선택**
        - `team_id`로 구독자를 바로 조회할 수 있도록 `SubscriptionByTeam` 테이블을 둔다.
        - 구독자가 많아지면 `(team_id, bucket_id)`을 파티션 키로 사용해 여러 파티션으로 분산한다.
            - 시간, 경기 → 고려하기
        - `bucket_id`는 `user_id`를 해시해 결정하고, 사용자별 알림 설정은 `Preference`에서 조회한다.
        - fan-out 단계에서 이벤트 종류, 푸시 허용 여부, 방해금지 시간을 확인해 발송 대상이 아닌 사용자를 제외한다.
    - **선택한 이유**
        - 전체 사용자를 탐색하지 않고 `team_id`를 기준으로 필요한 구독자만 바로 조회할 수 있다.
        - 인기 팀의 구독자를 여러 `bucket`으로 나누면 하나의 파티션에 데이터와 조회 부하가 집중되는 것을 줄일 수 있다. `bucket`은 `SubscriptionByTeam`을 나누는 DB 파티션 단위이며, 조회와 설정 필터링이 끝난 발송 대상은 별도의 `chunk` 단위로 나눠 `Delivery Queue`에 넣는다.
    - **트레이드오프**
        - 한 팀의 구독자를 조회할 때 여러 bucket을 읽어야 한다.
        - bucket 수를 변경하면 데이터 재배치가 필요할 수 있으므로 초기값을 정하고 규모에 따라 조정한다.
- Decision #5: **푸시 공급자별 장애 격리를 위해 Delivery Queue와 Sender Worker 분리**
    
    !image.png
    
    - **문제**
        - APNs와 FCM은 서로 다른 외부 서비스이므로 한쪽의 지연이나 장애가 다른 채널의 발송까지 막아서는 안 된다.
        - 일시적인 장애와 무효 토큰처럼 실패 원인에 따라 필요한 처리가 다르다.
    - **선택**
        - APNs와 FCM에 각각 `Delivery Queue`와 `Sender Worker`를 둔다.
        - `5xx`, timeout, `429`처럼 일시적인 실패는 backoff 후 재시도한다.
        - 공급자가 토큰을 무효로 판단한 경우에는 재시도하지 않고 해당 토큰을 비활성화한다.
        - 반복 재시도로 해결할 수 없는 작업은 `DLQ`로 보낸다.
    - **선택한 이유**
        - 한 공급자의 장애나 적체가 다른 공급자의 발송 경로로 전파되는 것을 막을 수 있다.
        - 성공 가능성이 있는 실패만 재시도해 불필요한 요청을 줄일 수 있다.
    - **트레이드오프**
        - 채널별 큐와 Worker를 운영해야 하므로 관리 대상이 늘어난다.
        - 공급자마다 오류 코드와 재시도 정책을 따로 관리해야 한다.
    
    —o—o—-
    
- Decision #6: **연속 이벤트의 알림 피로를 줄이기 위해 `coalescing`과 발송 상한 도입**
    
    !image.png
    
    - **문제**
        - 득점 이벤트가 짧은 시간에 연속으로 발생하면 사용자에게 여러 개의 푸시가 연달아 갈 수 있다.
        - 여러 경기를 구독한 사용자는 더 많은 알림을 받을 수 있다.
    - **선택**
        - 득점처럼 연속해서 발생할 수 있는 이벤트는 짧은 `coalescing window` 안에서 묶어 최신 스코어를 한 번에 전달한다.
            - **`coalescing`: 가까운 시간에 발생한 여러 이벤트를 하나로 합치는 것**
        - 경기 시작과 종료처럼 발생 횟수가 적고 의미가 분명한 이벤트는 묶지 않는다.
        - 사용자별로 경기당 푸시 알림 수에 상한을 둘 수 있게 한다.
    - **선택한 이유**
        - 모든 이벤트를 그대로 보내는 것보다 짧은 시간에 반복되는 알림을 줄이면서 중요한 경기 변화는 전달할 수 있다.
    - **트레이드오프**
        - 이벤트를 묶는 시간만큼 득점 알림이 늦어질 수 있다.
        - 묶음 시간과 경기당 상한은 실제 알림 수신 패턴과 사용자 반응을 보고 조정해야 한다.

## 4. 상세 설계

### 이벤트 수신과 중복 판별

스코어 피드는 `game_id`, `event_type`, `seq`를 함께 보낸다고 가정한다. 수신 API는 이 조합을 Event Inbox에 조건부로 기록한다. 이미 같은 키가 있으면 기존 이벤트로 보고 처리하지 않는다.

새 이벤트만 `event_id`를 발급해 Event Queue에 기록한다. 큐 기록이 완료된 뒤에만 `202 Accepted`를 반환한다. 이 응답은 발송이 끝난게 아니라 안전하게 접수됐다는 뜻이다.

### 구독자 조회와 fan-out

Fan-out Worker는 팀 또는 경기 기준으로 구독자를 조회한 뒤, 이벤트 종류·알림 권한·방해금지 시간 같은 설정을 먼저 적용한다. 발송 대상은 1,000건을 초기값으로 하는 chunk로 나눈다.

이벤트 전체를 한 작업으로 두면 일부 실패에도 처음부터 다시 처리해야 하고, 건별 메시지로 쪼개면 큐 자체가 병목이 될 수 있다. chunk마다 진행 위치를 남겨 두면 실패한 구간만 다시 처리할 수 있다. 인기 팀처럼 구독자가 많은 경우에는 팀 ID에 bucket을 붙여 조회 부하를 나눈다.

### 발송과 재시도

Sender Worker는 채널별 큐에서 작업을 가져와 APNs 또는 FCM으로 보낸다. 발송 직전에는 `(event_id, device_token)`을 키로 중복 여부를 확인한다. 이 처리는 내부 재시도로 인한 중복을 줄이기 위한 것이며, 외부 푸시 서비스까지 포함한 exactly-once 전달을 보장하지는 않는다.

일시적인 네트워크 오류와 5xx는 지수 백오프와 지터를 적용해 재시도한다. 429 응답은 공급자가 안내한 대기 시간과 채널별 속도 제한을 따른다. 더 이상 쓸 수 없는 토큰은 재시도하지 않고 비활성화한다. 반복 실패 작업은 DLQ로 옮겨 원인을 확인한 뒤 별도로 처리한다.

### 사용자 경험과 장애 대응

득점처럼 짧은 시간에 연속으로 발생할 수 있는 이벤트는 잠시 모아 최신 점수로 묶어 보낸다. 반면 경기 시작·종료처럼 사용자가 기다리는 이벤트는 즉시 발송한다. 방해금지 시간이나 수신 상한에 걸린 알림은 푸시 대신 인앱 알림함에 남긴다.

Dedup Store를 확인할 수 없으면 추측해서 보내지 않고 해당 발송을 멈춘다. 중복 푸시는 회수할 수 없지만, 멈춘 작업은 큐에 남아 복구 후 다시 처리할 수 있다. 잘못된 문구나 대상이 감지되면 운영자가 즉시 발송을 중단할 수 있도록 kill switch를 둔다.

## 5. 운영 기준

운영에서는 이벤트 수신부터 마지막 발송까지의 지연, 채널별 성공률, 재시도·DLQ 비율, 무효 토큰 비율을 확인한다. 지연이 길어지면 큐 적체와 공급자 제한을 먼저 점검하고, 필요하면 Worker 수와 chunk 크기를 조정한다.

초기값은 `chunk = 1,000`과 득점 알림 묶음 시간이다. 실제 운영에서는 큐 지연, 재시도율, 사용자당 수신 건수와 알림 권한 해제율을 함께 보며 조정한다. 모든 알림을 무조건 즉시 보내는 것이 아니라, 중복과 오발송을 줄이면서 중요한 경기 정보를 제때 전달한다.
